### スマホ実機相当の監査 — 何が壊れているかを実測した

- **背景と目的**:

- **測って分かったこと（症状と原因）**:
  - **惑星が惑星として読めるのは `far`（俯瞰）だけ。** `near`（標準）と `building` では画面下 55〜60% が地面で埋まり、丸みが一度もフレームに入らない。原因は構図が横長前提であること自体ではなく、**縦長では `frameDistance` が幅側の半画角で距離を決める**（`Math.min(halfVertical, halfHorizontal)`）ため、アスペクトが 0.46 まで落ちると被写体が縦方向に大きくはみ出すこと。
  - **カードが被写体を完全に覆う。** `CARD_SHARE = 0.3` は「フレーム幅の 3 割をカードに譲る」設計だが、390px 幅でカードの実測は **x = 28〜362（幅 334px、画面の 86%）**。3 割 ≒ 117px 横にずらしても被写体はカードの裏から出ない。`building` のスクショで、寄ったはずの建物が一切見えていないのがその帰結。`ORBIT_CARD_SHARE = 0.22` も同様。**この 2 定数は「カードは画面の一部しか占めない」を暗黙の前提にしている。**

  - **モバイルメニューがシートの上に居座る。** Products を開いた直後のスクショでドロップダウンが開いたままタイトルを覆っていた。
  - **About のクロールがタッチでほぼ動かない。** 実測で **500px 指を滑らせて進んだのは 73px**（うち約 32px は 0.5 行/秒の自動再生ぶん、正味 ≒ 40px）。原因は `scrollCatchUp` の rAF ループが毎フレーム `scrollTop` を `scrollTargetRef` へ引き戻すこと。**ホイールには専用ハンドラがあるがタッチには無い**ので、ネイティブのタッチスクロールが書いた `scrollTop` が即座に打ち消される。

- **測るときに踏んだ罠**:
  - **About の `scrollTop` は外から書いても戻される。** `page.evaluate` で `scrollTop = 600` と書いた直後に読むと 172 になっていた。rAF の catch-up ループが `scrollTargetRef` へ引き戻すため。**About を任意の位置で撮るには `scrollTargetRef` を動かす入力（ホイール / タッチ）を送るしかない。** これは不具合ではなく設計（`scrollCatchUp` の doc コメント参照）だが、スクショの撮り方としては verification.md の「別実行で測った値を使い回さない」と同じ種類の落とし穴。

### スマホのカメラ構図 — `NEAR_VERTICAL_SHARE` は触らず、別定数を実測で決めた

- **最初の導出が間違っていた（記録として残す）**: 「カードが下に来るのだから、惑星を上へ持ち上げて空けよう」と考え、`HANDHELD_VERTICAL_SHARE = HANDHELD_HEADER_SHARE - HANDHELD_RAIL_SHARE = -0.147` という**負の値**を置いた。導出自体は筋が通っていたが、**前提が違った**——「惑星の円盤をヘッダーとレールの間に収める」という式は `far` の話で、`near` では惑星は円盤ではなく**画面いっぱいの風景**である。実測すると地面が**フレームの94%**を覆い、水平線は画面の上に消えていた。

  | share | 水平線の y | 地面の占有率 |
  | --- | --- | --- |
  | 0.0 | 25 | 91% |
  | 0.20 | 121 | 88% |
  | 0.35 | 186 | 80% |
  | 0.50 | 256 | 71% |
  | 0.636（PC） | 324 | 65% |

### HOME を押すと詳細ページが開いてしまう不具合

- **症状**: スマホでカードの上の HOME ボタンを押すと、ホームへ戻ると同時に詳細ページが開く。
- **原因**: レールのジェスチャ判定（`onPointerDown` / `onPointerUp`）が**レールのルート**に付いていて、バブリングで中身のイベントを全部拾う。HOME ボタンのタップは移動量ゼロなので `isRailTap` が真になり、`onOpen()` が走っていた。ボタン自身の `onClick`（`closeToHome`）も走るので、**開いてから閉じる**という2つの状態遷移が続けて起きていた。
- **修正**: `event.target.closest("button, a")` に当たったプレスは、レールのジェスチャとして扱わない。**コントロールごとに覚えるのではなく DOM に訊く**形にしたので、あとからレールに足したものも自動で対象外になる。
  - シーンの `isInteractive` は同じ歩き方をするが、**ここでは再利用できない**——あちらは `[data-ui]` にも当たり、それはレール自身だから。
- **なぜ設計段階で見落としたか**: カードの上に載せるものが「カードの一部」なのか「カードの上の別のもの」なのかを、**ジェスチャの側が区別する仕組みを持っていなかった**。矢印だった頃も同じ穴が空いていたが、あのときの矢印は「詳細を開く」ボタンで、誤爆の結果が本来の動作と一致していたので**症状として現れなかった**。役割を HOME に変えた瞬間に露見した。
- **検証**: HOME をタップ → シートは開かない（直後・9秒後とも false、hash も変化なし）。カード本体をタップ → 開く（true）。横スワイプは1つ送れる。空タップの停止／再開（差分画素 80,700 ↔ 20）とドラッグでの誤爆なしも再確認。

### カードを薄くし、ドラッグに追従させ、並びを「間を空けた3枚」にした

- **依頼は3つ**: (1) カードをもう少し薄く、角丸を弱く。(2)「スライドしたら次のカードに移るが、**保持**できるように」。(3) 並びを参考画像のようにする。

- **(2) の「保持」を実装前に確認した。** 言語化しづらいという申告があったので、コードから読み取れる候補を3つ出して選んでもらった——(a) スワイプ後も自動周回が止まらず数秒で別のカードへ流れる、(b) ドラッグ中に見た目が動かない、(c) HOME や詳細ページから戻ると位置を失う。**答えは (b)「ドラッグ中の指に追従してほしい」**。
  - **確認して正解だった。** 文面（「次のカードに移るが」）だけ読むと (a) に見え、その線で直すと**アイドル周回を止める**という別物の変更になっていた。アイドル周回はジオラマが生きていることの中身で、止めるかどうかは見た目の手触りとは別の判断。
  - なお現状でも 36px 未満のドラッグは `stepForRailDrag` が 0 を返して**同じカードに留まる**。足りなかったのは判定ではなく、離すまで何も動かないという**無反応**のほうだった。

- **追従は「見た目だけ」に閉じ込めた。** 3枚を包む transform 専用の `motion.div` を1枚足し、`useMotionValue` を `style={{ x }}` に直結して pointermove ごとに書く。離したら同じばね（`RAIL_SPRING`、カードのスロット移動と共有）で 0 へ戻す。
  - **カメラはこの値を読まない。** 読ませた瞬間、却下済みの「スクロールコンテナ」と同じ閉ループになる（`docs/scene-invariants.md`「カードとカメラを相互に更新しない」）。送るかどうかは従来どおり離した瞬間の `stepForRailDrag(dx, dy)` だけが決め、追従量は判定に入らない。
  - **state ではなくモーション値**にしたのは、pointermove ごとの `setState` が1ドラッグでレールを60回再描画するから。既存の `dragStart` が ref なのと同じ理由。
  - **包む `motion.div` に `absolute inset-0` を明示した。** `x` が付くと transform ありの要素になり、中の `absolute inset-0` の**含みブロックになる**。箱を持たせないと高さ auto（中身は絶対配置なので0）に対して `top:0;bottom:0` が解決し、**カードが高さ0に潰れる**。
  - **縦優位のドラッグでは追従させない。** `stepForRailDrag` が縦優位を拒む理由（ジオラマへ向けたジェスチャ）は見た目にもそのまま効く。
  - 追従量は隣のカードの位置で頭打ちにした。窓は3枚しかないので、それ以上引くと**4枚目ではなく空白**が出てくる。

- **(3) 並びを重ね（0.84）から間空け（1.082）へ。** 参考画像は両隣が中央カードに**乗っていない**。
  - **px ではなく比で導いた。** 参考画像のカードは画面の85%、こちらは78vw なので、隙間の px をそのまま持ってくると見た目が一致しない。参考では両隣が 780 の画面に対し 35.5 見えている＝**4.6%**、390px なら 18px で、これはカードの padding（16px）の内側——だから**文字が出ず白い縁だけ**になる。逆算して隙間 43 − 18 = 25px、25/304 で **1.082**。
  - **両隣の `scale(0.9)` と `opacity: 0.45` も外した**（参考画像では同じ大きさ・同じ白）。どれが説明中かは間隔とドットが言う。副次的に、`scale` で両隣が枠より7px 下に出る——レール上端の実測を1度狂わせたあの罠——が消えた。
  - `railLayout.test.ts` の2件を「重なること」から「**隙間が空くこと**」「隙間が広すぎて画面から消えないこと」へ書き換えた。

- **(1) 薄く・角丸を弱く**: `rounded-3xl`→`rounded-xl`、`shadow-xl shadow-black/20`→`shadow-md shadow-black/10`。高さ（`CARD_HEIGHT = 132`）と padding は触っていない——コピーの行数に合わせて詰めてある値なので、影と角だけで「薄さ」を出した。ばねの定数は `RAIL_SPRING` に1つへまとめ、カード側と戻り側で同じ数を2箇所に持たないようにした。

- **ヘッドレス検証の罠（新規）**: `page.evaluate` で位置を刻んでもばねが**1pxも進まない**。`isAnimating()` は true のまま。原因は**ヘッドレスでは rAF がフレームを要求されたときしか回らない**ことで、`evaluate` はフレームを起こさない。`page.screenshot` を挟むと進む。**モーションの検証はスクリーンショットで刻む**こと。危うく「framer-motion の `animate()` が動かない」と誤診しかけた。
- **検証**: 390×844 で、静止（両隣は白い縁だけ・中央カードとの間に隙間）、ドラッグ中（3枚が指と一緒に左へ、右から次が出てくる）、離したあと（ばねで整列し、`stepForRailDrag` の送りが成立して 経歴・活動 へ、ドットも3番目へ）をそれぞれ撮影して確認。`npm test` 462件、`tsc --noEmit`・`lint` クリーン。

### 技術スタックのアイコンを、スマホではタップで点灯させる

- **症状**: スマホだと Skills のアイコンが**全部グレーのまま**で、ブランド色が一度も出ない。
- **原因**: 色を出しているのは `group-hover:text-[var(--hover-color)]` だけ（枠線・拡大・ラベルの濃さも同様）。**ホバーの無い画面には出口が無かった**。PC ではポインタが常にどこか1つの上にあるので問題として現れない。
- **修正**: `useHandheld()` が真のときだけ `onClick` を生やし、押されたタイルを `litSkill` として持つ。**PC 側の `hover:` は一切触っていない**——スマホで具合が悪いからといって PC の値を書き換えない、の通り。判定は既存のフック1つで、2つ目の述語は作っていない。
- **同時に点くのは1つだけ**にした。ホバーが1つずつなのはポインタが1つだからで、タップで次々に点いて**残る**と、読み進めるほど画面がスクラッチカードになる。同じタイルをもう一度押すと消える。

- **検証**: 390×844 で `#skills` を開き、計算済みスタイルで確認——タップ前は3枚とも `lab(65.9 …)`（`text-gray-400`）、TypeScript をタップすると `rgb(49, 120, 198)`（= `#3178C6`、定義どおりのブランド色）になり**他の2枚はグレーのまま**、もう一度タップで戻る。枠線・ラベル・拡大も同時に効くことをスクリーンショットで確認。`tsc --noEmit`・`lint` クリーン。

### スマホの視点を2段とも引いた——「惑星の縁が画面の3分の1」を1つの規則にした

- **依頼**: 俯瞰視点は今よりもう少し俯瞰に。標準視点はもう少し俯瞰にしたうえで**画面の3分の1は背景が見える**ように（惑星の位置を下げたい）。

- **最初に PC 側を変えてしまった。** 依頼文に画面の指定が無かったので両方に効く定数（`ORBIT_RADIUS` / `NEAR_ORBIT_RADIUS`）を動かしたが、**話はスマホ側だった**。PC は元のまま（100 / 50、参考写真由来）に戻し、スマホ用の高度を別に足す形にやり直した——CLAUDE.md の「PC 用の定数をスマホの都合で書き換えず、スマホ用の定数を別に足す」を、**逆向き（スマホの都合で PC を動かす）にやっていた**ことになる。`nearVerticalShare(handheld)` と同じ構造がすでにあったのだから、最初からそちらに乗せるべきだった。
  - **どちらの画面の話かは、依頼文に書かれていなくても確定させてから触る。** 構図の依頼は「どのフレームの話か」が決まらないと値が決まらない（PC は16:9、スマホは0.46で下端にカードレールがある）。

- **スマホの高度は1つの規則から解いた: 惑星の縁が画面の3分の1の位置に来る（`HANDHELD_PLANET_TOP = 1/3`）。** 惑星の中心は注視点そのものなので画面の `0.5 + lean/2` に来て、縁はそこから円盤の半分だけ上。つまり必要な円盤の高さは `1/3 + lean` で、**俯瞰はリーンが無いので 1/3、標準は `1/3 + HANDHELD_VERTICAL_SHARE`**。2段の違いはリーンの有無だけになる。
  - 距離に直すのは `orbitRadiusForDiscHeight(share)`（円盤の直径は画面高の `tan(asin(R/D))/tan(fov/2)`、その逆関数）。**PC 側はこの式を使わない**——あちらは参考写真が距離を直接指しているので、解き直すと誰も頼んでいない構図の変更になる。
  - 結果: 標準 50 → **77.9**、俯瞰 100 → **122.8**（スマホのみ）。`orbitRadiusForZoom(zoom, handheld)` が選ぶ。`handheld` は既定値を持たせず必須にした——**渡し忘れたらスマホが PC の構図で描かれる**という、この定数が存在する理由そのもののバグになるため。

- **390×844 の実測**（`docs/verification.md` の「幅の半分以上が背景でなくなる最初の行」＝水平線）:

  | 段 | 惑星の縁（式） | 水平線（実測） |
  | --- | --- | --- |
  | 標準 | 143 → 281px | **125px (14.8%) → 267px (31.6%)** |
  | 俯瞰 | 248 → 281px | **250px (29.6%) → 279px (33.1%)** |

  標準は空が画面の15%しか無かったのが**ちょうど3分の1**になった。俯瞰はもともと3割近くあったので動きは小さい。

- **リーンは触っていない。** 同じことは `HANDHELD_VERTICAL_SHARE` を上げてもできるが、スマホのリーンの上限は好みではなく**カードレール**で決まっている（0.20 が折れ点、0.25 で一周20点中11点が隠れる）。引くほうを選ぶと空が開くうえに押し下げ量 `lean·radius·H/(2·depth)` は**縮む**——半径は +56%（50→77.9）だが深さは +142%（19.6→47.5）なので、押し下げは 215px → 138px——ので、点線は悪くなるどころか良くなる。`cameraLayout.test.ts` にこの不等式をピン留めした。

- **検証**: 390×844 で標準・俯瞰の両方を撮影（俯瞰へは**実際のピンチ**——`pointerdown` 2本を canvas に投げて距離を160→80に縮める——で入り、ジェスチャ経路ごと確認）。PC（1440×900）は変更前と同じ構図に戻っていることを実測で確認（球の上端 323px → 324px、街込み 273px → 275px、差はアイドル回転ぶん）。`tsc --noEmit`・`lint`・`npm test` 470件クリーン。

- **踏んだ罠**:
  - **zsh は `set -- $c` で語分割しない。** 候補値を `"58:0.66"` のペアで回して `set -- $c` を使ったら `$1` に `58 0.66` が丸ごと入り、`sed` が `export const NEAR_ORBIT_RADIUS = 58 0.66;` を書いた。dev サーバーはパースエラーになり、**撮れた3枚は全部エラーオーバーレイ**だった。`${c%%:*}` / `${c##*:}` に変えた。
  - **ヘッドレスの PNG を読む手段が無い。** この環境には PIL も sharp も無いので、`zlib` で PNG デコーダ（フィルタ0〜4）をスクラッチパッドに書いた。行ごとに非背景画素を数え、**幅の半分**を超えた行を水平線（スマホ）、**幅の1割**を超えた行を球の上端（PC）とした。
  - **構図をピクセルで測るときは DOM を消してから撮る。** ヘッダー・カード・点線の SVG を `visibility: hidden` にしないと、横に伸びる点線が1行で300px以上の非背景画素を作り、上端を誤判定する。ヘッダーのロゴも「惑星の上端」を毎回 y=28 と答えさせていた。

### 2本指ジェスチャを、PC と実機スマホの両方で成立させた

- **報告された症状は「PC と実機で結果が逆」の2つ**: (1) 2本指ズーム（俯瞰⇄標準）は**実機スマホでは効くが PC 検証では効かない**。(2) 2本指スクロール（軌道の飛行・自己紹介文のスクロール）は**PC では効くが実機スマホでは効かない**。

- **原因は「入力の経路が片方の環境にしか無い」こと。** 同じ「2本指」でも、届き方がまったく違う。
  - **PC のトラックパッドのピンチは pointer イベントではなく `wheel` で来る**（`ctrlKey: true` 付き。ブラウザがページズームに使う流儀）。`useViewInput` のピンチは `pointerdown` が2つ来ることを前提にしていたので**発火しようがなかった**。しかも素通りして通常のホイール処理に落ちていたので、**ピンチするとツアーが進む**という誤動作になっていた（無反応より悪い）。
  - **スマホには `wheel` が無い。** ツアーの前進も自己紹介のスクロールも `wheel` にしか繋がっていなかったので、指では動かしようがなかった。2本指は「ピンチかどうか」だけを見て早期 `return` していたため、**平行移動は完全に無視**だった。
  - **自己紹介はもう一段深い。** コラムは `overflow-y-auto` の実スクロール要素なので指では動く——が、`scrollTargetRef` を正とする毎フレームの追従ループ（`scrollCatchUp`）が **次のフレームで引き戻していた**。「ホイールは preventDefault しているので他に動かすものは無い」という前提がタッチで崩れていた。無言で失敗する形（テキストがただ動かない）だったのが厄介。

- **直し方は3つ、どれも「もう片方の経路を足す」形にした。**
  1. **2本指に2つのモードを持たせた**（`twoFingerGesture()`）。指の**間隔が変われば**ズーム、**一緒に動けば**ツアーの飛行。最初に決まったほうがその手離しまでジェスチャを保持する（ラッチ）。
  2. **ctrl+wheel をピンチとして拾う**（PC のトラックパッド）。小刻みなデルタの列なので合計が `PINCH_WHEEL_THRESHOLD` を超えたら1回だけ段を切り替え、220ms 静かになるまで再発火しない。`preventDefault` はブラウザのページズームを止めるために必須（`userScalable: false` はこのジェスチャを止めない）。
  3. **自己紹介は「自分が書いていない `scrollTop`」を採用する。** 追従ループが書いた値を `writtenTopRef` に控えておき、`handleScroll` でそれと1px以上ずれていたら**指が動かした**と判断して `scrollTargetRef` をそこへ移す。指1本でも2本でも、ブラウザの慣性も、そのまま効く。

- **ズームとスクロールの判定は「どちらが先に閾値を超えたか」ではなく「どちらが大きいか」。** 片手の親指を固定して行うピンチは、間隔が変わる量の**半分だけ中点も動く**。先着順にすると、間隔が60pxのうち48pxしか開いていない時点で中点が24pxに達して**スクロールと誤判定**する（＝片手ピンチで高度が切り替わらない）。`|spread|` と `|travel|` を直接比べる形にしてある。この awkward case はブラウザで指2本を再現しながら詰められないので、`viewGesture.ts` に純関数として切り出し、`viewGesture.test.ts` に「片手ピンチ」「平行スワイプ」「途中でどちらでもない」を置いた。

- **2本指スクロールの速さは `DRAG_SENSITIVITY`（0.002 rad/px）＝1本指ドラッグと同じ率にした。** ホイールの `WHEEL_SENSITIVITY`（0.0004）をそのまま使うと、トラックパッドの慣性が無いぶん**790px 引いてツアーの1/20**という体感になる。同じ指が同じ距離動いたら世界も同じだけ動くべきで、違うのは**どの経路を動くか**だけ。

- **「建物正面視点」はピンチの巡回に入れていない**（依頼どおり）。`onPinchZoom` は `setOrbitZoom` だけを呼び、セクションに寄っている間は `useViewInput` 全体がロックされる。実測でも、俯瞰でもう一度つまんでも俯瞰のままだった。

- **検証**（すべてヘッドレスの実測）:
  - PC 1440×900: 標準 →（ctrl+wheel でつまむ）→ **俯瞰** → もう一度つまんでも**俯瞰のまま** →（広げる）→ **標準**。通常のホイールは従来どおりツアーの飛行（停止状態で前後を比べて画素の30.9%が変化、段は不変）。
  - スマホ 390×844: 空タップで停止 → **何もしない4秒で画素の変化 0.0%** → 2本指で上へ510px → **47.8%が変化**（＝飛んだ）。ピンチで俯瞰／標準を往復。
  - 自己紹介: コラムの `scrollTop` を 9 → 309 に動かす（ブラウザが指で行うのと同じこと）と、2.5秒後も **313**。従来はここが引き戻されて動かなかった。
  - `tsc --noEmit`・`lint`・`npm test` 476件クリーン。

- **踏んだ罠**: **合成した `PointerEvent` には `offsetX` が生えない**（コンストラクタが `clientX` しか受け付けない）ので、R3F のレイキャストに乗る操作——空タップでの停止など——は `Object.defineProperty` で足してから投げる必要がある。`docs/verification.md` に既出の罠だが、今回の停止ジェスチャでも同じところを踏んだ。

### `reference/now`にムード参考12枚を収集。ネオン発光×ブルームの技術検証を`sandbox/voxel-lab.html`で実施
