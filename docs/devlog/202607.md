### 報告された3つの不具合を修正
- **開く時のカクつき**: 計測の結果、原因は2つ。
  - Skills を開くと `cdn.jsdelivr.net` へ **28リクエスト**。各スキルは最初からローカルの react-icons を持っていたのに、リモートURLが優先されていた。→ 28 → 0。
  - Products の画像が **16MB の生 PNG**（`imadoko.png` は 6.8MB / 3420px を高さ192pxのカードに表示）。静的エクスポートのため `next/image` は `unoptimized` 強制でリサイズが効かない。sharp で 1600px / WebP へ再エンコードし **16MB → 337KB（97.9%減）**。
- **戻る境界の曖昧さ**: スペーサーが 150vh、ビューポートが 100vh。パネルが画面から消えるのは progress 0.67 の時点で、**残り半画面ぶんが死に区間**だった。スペーサーを1ビューポートに揃え「消える瞬間＝戻る瞬間」を一致させた。慣性で数px手前に止まると二度とイベントが来ないため閾値 0.98、開いた直後のロックは 1200ms → 450ms。
- **視点が2〜3回切り替わる**: `camera-controls` の `_createOnRestPromise` は呼び出しの識別子を持たず、次の `rest` で誰の Promise も解決する。2つの effect が1個の boolean を共有していたため、古い飛行の `.then` が飛行中にフラグを倒し、`useFrame` が毎フレーム上書きを始めていた（1台のカメラに2人の書き手）。飛行ごとにトークンを発行して解決。あわせて、タブ切替時に「ホームの角度」を建物視点の角度で上書きしていたバグも修正。

### カメラモデルの作り直し（参考サイトの記事に基づく）
- 開発者本人の解説記事を読み、以下が判明。
  - **層の分け方**: 拍動する円形アイコンは WebGL（他の3Dオブジェクトに隠れる）、点線コネクタは DOM、ツールチップは DOM 最前面。
  - **スクロール同期のカメラパスは一度作って断念**（3D酔いの懸念）。最終形は単純な周回。
  - **FPSガバナー**: 操作中60fps / 静止30fps / **canvas がコンテンツの裏に隠れている時 0.5〜1fps**。
- **スクロール連動補間を削除**: 白い不透明パネルの裏で毎フレーム `lerpLookAt` を回していた。誰にも見えず、かつ「分岐は state・入力は ref」の時間差により視点バグの原因そのものだった。
- **FPSガバナー実装**: パネルが画面を覆いきってから `frameloop="demand"` + 1秒ハートビート。実測（WebGLドローコール計測）で覆われている間 **毎秒1描画に固定**、スペーサーで復帰することを確認。
- **慣性の流入を遮断**: 強くフリックして閉じるとカメラが回り出す症状。慣性スクロールは指を離した後も1〜2秒イベントを出し続け、ロック解除直後の残りが回転に化けていた。「ロック中に始まったストリームは、ホイールが静かになるまで受け付けない」方式で解決。
- **戻り先の仕様変更**: 「離れた時の角度を記憶して戻る」を廃止。スクロールで離脱 → **全景の距離のまま、そのエリアが正面に来る角度へ**。ロゴ/HOME → 毎回同じ固定視点。カメラの行き先を決める処理を1つの effect に統合。

### カードとマーカー
- **カードをカメラから導出**: `activeSection` 依存をやめ、周回の方位角から「今どのエリアが正面か」を求めて表示。カードがカメラを動かし、カメラがカードを変える双方向は必ず喧嘩するため一方向にした。実測で、周回に従いカードが順に切り替わること、技術スタックをスクロールで閉じた直後に「技術スタック」カードが出ることを確認。
- **エリアマーカー**: 各エリア上空に脈打つドットをスプライトで配置。深度バッファに乗るため建物が手前にあれば自然に隠れる。正面のドットはアクセントカラーで拡大。アンカー高さは現行の建物実寸に合わせた手調整値（モデル変更時に要調整）。

### カード → マーカーの点線（DOM）
- **層の分担**: マーカーは WebGL（建物に隠れてほしい）、点線は DOM（常に最前面の平面）。参考サイトの記事と同じ分け方。
- **毎フレームの受け渡しを React state に通さない**: シーンが持つカメラ情報を DOM 側が必要とするが、state 経由にすると60回/秒の再レンダーが走り、描画と同じメインスレッドを奪い合う。小さな購読チャンネル（`3d/markerScreen.ts`）を作り、シーンが push、線側は SVG の属性を直接書き換える方式にした。
- **描画**: 20個の `<circle>` をカードの角からマーカーまで二次ベジェ上に配置。半径を 4.5px → 1.8px へ先細りさせ、弦に対して垂直方向に少し反らせて弧にしている。
- **可視判定**: 当初はカメラ前後（`z < 1`）しか見ておらず、マーカーが画面上端の外（実測 y = -238）に出ると線が画面外へ飛んでいた。ビューポート内かどうかも条件に追加。

- **判明した制約**: 全周を回して実測したところ、**5エリア中「制作実績」だけ点線が常に非表示**。ピンクタワーが高く、マーカーがホーム視点の画面上端より上に出るため。マーカー高さを 13.3 → 10.4（アンテナではなく塔屋を基準）に下げても解消せず、**原因はマーカーではなくホーム視点の画角そのもの**（現在の `HOME_RADIUS = 24` では高い建物が上で見切れている）と確定。次の A1（`fitToBox` によるエリア単位の構図決定）で対応する。

### ホーム視点の画角を実測から決め直し
- **実測**: シーンに一時的な計測コンポーネントを差し込み、ワールドと各エリアのバウンディングボックスを取得。
  - ワールド全体 y -7.3 〜 22.3（上限は紙吹雪と雲で、構図の制約にすべきでない）、XZ はおよそ ±14。
  - 建物の高さ: 制作実績 **12.2**（アンテナ先端）、技術スタック 7.5、自己紹介/お問い合わせ 4.6、経歴・活動 3.8。
- **原因の特定**: 従来はカメラ高さ11・注視点 y=1 で、俯角 22.6°。垂直画角45°に対し**視野の上端が水平から0.1°**しかなく、カメラの目線より高いものは原理的に写らない。ピンクタワー(12.2)は必ず切れていた。
- **修正**: 注視点を地面(y=1)ではなく**コンテンツの中央(y=3.5)**へ。俯角16.1°となり塔が収まる。半径は 24 → 26。角度計算をスクリプトで検証してから適用した。
- **初回マウントでホーム構図が適用されていなかった**: `<Canvas camera>` は位置しか設定できず注視点は原点のままだったため、起動直後は上記の修正前より悪い俯角で回っていた。マウント時にトランジションなしでホーム構図へスナップするよう修正。
- **マーカー高さの手調整を廃止**: 建物の実バウンディングボックスの上端＋クリアランスで実行時に決める方式へ。建物が育っても屋根に埋まらない。
- **結果**: 全周を実測し、**5エリアすべてで点線が表示**されることを確認（従来は制作実績のみ常時非表示）。

### エリア単位の構図をサイズから計算（`fitToBox` は使えなかった）
- **`fitToBox` を採用しようとして撤回**: 実装を読むと冒頭で `roundToStep(theta, PI_HALF)` によりカメラ角度を90°刻みに丸め、正面・真横・真上のいずれかへスナップする。ジオラマの斜め俯瞰が壊れるため使用不可。API の説明だけを見て推奨したのは誤りだった。
- **代替として自前の純粋関数を用意**:
  - `frameDistance(radius, fov, aspect)`: 対象の外接球が収まる距離。垂直・水平の**狭い方**の半画角で計算するため、縦長ビューポートでも収まる。従来は全建物が距離13固定で、12単位のタワーと4単位の図書館が同じ扱いだった。
  - `framePose(target, azimuth, distance, tilt, sideways)`: そのエリア固有の方位角から、指定距離・俯角で見る配置を返す。`sideways` は注視点を横へずらすもので、**被写体を画面右へ寄せて左のカードを避ける**。
  - `aimOffset(distance, fov, aspect, share)`: 避ける量を「フレーム幅の何割か」から算出。距離が変われば必要量も変わるため定数では足りない。
- **検証**: 変異テスト2種（`sin` → `tan` の定番ミス、狭い方ではなく広い方の半画角を使う）で「被写体が実際に画角に収まる」テストが落ちることを確認。テスト計86件。

### カードのジェスチャ（A5）
- **タップで詳細ページ、上下スワイプで隣のスポットへ回転**。
- **既存のジェスチャとの衝突を回避**: キャンバス側はタッチの縦スワイプをカメラ回転に割り当てているため、カードがその操作を専有する必要がある。`Scene` の `isInteractive()` が `[data-ui]` を除外する設計になっていたので、カードに `data-ui` を付けるだけで解決した。
- **タップとドラッグの判別**: 移動量10px未満をタップ、縦44px以上かつ横移動より大きい場合をスワイプとする閾値方式。
- **「隣」の定義**: `SECTIONS` はオブジェクトのキー順であって周回順ではない。**方位角でソートした順序**（`SECTIONS_BY_AZIMUTH`）を用意し、`adjacentSection()` で前後に1つ進む形にした。端を越えたら反対側へ回り込む。
- **回転の指示**: 既存の周回ターゲット角を書き換えるだけ。カメラは慣性付きでそこへ寄っていき、カードは角度から導出されているので自動的に追従する（新たな同期処理は不要）。

### 描画の軽量化（B）
- **マテリアル**: `meshStandardMaterial` → `meshLambertMaterial`。ボクセルは一様なマット色で metalness / roughness の変化を表現していないため、物理ベースの計算は誰も使わない応答を計算していた。参考サイトの開発者も実測の末に同じ材質へ行き着いている。
- **シャドウマップ**: 2048 → 1024。ブロック状の形状が落とす大きく柔らかい影なので、解像度は見えない精細さのために4倍のコストを払っていた。
- **実測**: フレーム間隔の中央値 **755ms → 571ms**（1.31fps → 1.75fps、約25%の軽量化）。ソフトウェアレンダリング環境での絶対値なので実機とは異なるが、シェーディングと影パスのコスト削減自体は実在する。見た目はスクリーンショットで確認し、パステルの質感は維持されている。

### URL とブラウザ履歴（C）
- **なぜ必要か**: これまでアドレス可能な状態が一切なく、**戻るボタンでパネルが閉じずサイトから離脱**し、特定セクションへのリンクも共有できなかった。
- **パスではなくハッシュを採用**: 単一の静的HTMLに3Dシーンが1つ載る構成なので、実ルートにすると「毎回ワールドを再読込」か「Canvas をレイアウトへ引き上げる大改造」のどちらかになる。ハッシュなら書き出し構成に手を入れず、戻るボタンとリンク共有が今日手に入る。
- **実装で踏んだ罠2つ**:
  1. 「URL 追従中は書き戻さない」フラグを置いたが、`activeSection` が変わらない場合は同期 effect 自体が再実行されず**フラグが立ちっぱなし**になり、次の操作が丸ごと無視されていた。フラグは不要で、**「今のハッシュと一致するなら何もしない」という比較だけで十分**（URL 由来の状態は必ず一致するため）。
  2. 到着時のハッシュを読む前に同期 effect が走り、**`#skills` 付きで開いても即座に消されていた**。読み取り完了までは書き込まないガードを追加。
- **実測**: 開く→`/#products`、戻る→パネルが閉じる、進む→再び開く、`#skills` の直リンク→Skills が開いた状態で着地、をすべて確認。
- **残る制約**: セクションの中身はクライアント描画のままなので、**プリレンダーされた HTML には含まれない**（JS を実行しないクローラからは見えない）。これを解消するには実ルートへの再構成が必要で、別途判断が要る。

### マーカーのホバー／タップ、点線の可変本数と破線化
- **マーカーにホバーとクリックを追加**: ホバーで拡大＋カーソル変更、クリックでそのエリアへ寄る（建物クリックと同じ着地点）。
- **点線を可変本数・等間隔に**: 従来は固定20個だったため、マーカーが遠いと間隔が伸び、近いと詰まっていた。曲線を細かくサンプリングして**弧長**を積算し、一定間隔（20px）で配置する方式へ。本数は長さから決まる（実測で6〜23本、間隔は 20px ±0.1px で一定）。ベジェのパラメータを等分すると曲がり部分で詰まるため、弧長で歩く必要がある。
- **デザインを円から破線へ**: 各マークを曲線の接線方向に沿った短い線分にした。奥に向かって長さと太さが細くなる。

- **その過程で重大なバグを発見**: **キャンバスがポインタイベントを一切受け取っていなかった。**
  - `elementFromPoint()` でシーンの上を叩くと `CANVAS` ではなく `MAIN` が返っていた。キャンバスのラッパーが `-z-10` で `<main>` の下に潜っていたため。
  - つまり `ProceduralObjects` の `Anchor` に実装されていた**建物のホバー／クリックは、ずっと死んでいた**（7月のログには動作確認済みと書かれているが、実際にキャンバスをクリックする検証ではなかったと思われる）。
  - `-z-10` → `z-0` に変更して解消。上に乗る要素はそれぞれ自前の z-index を持っているため影響なし。修正後、シーン上のホバーでカーソルが `pointer` になり、マーカーのクリックでセクションがフォーカスされることを実測で確認。
- **役割と docs 運用を明文化（追記）**: 「開発して終わり」にならないよう、`CLAUDE.md` に「あなたの役割はプロダクト開発 ＋ docs 作成」を明記した。あわせて devlog だけだった更新ルールを **docs 全体**へ広げ、`devlog` / `tech.md` / `voxel-object-creation.md` / `README.md` / `CLAUDE.md` のどれをいつ更新するかを表にした。devlog は毎回、他は変更の中身に応じて。

### マーカーと点線の調整
- **建物側の操作を撤去**: ホバーの浮上とクリックを削除し、建物は完全に固定。操作対象はマーカーのみとした。1つの行き先に当たり判定が2つある状態を解消し、あわせて「マーカーが乗っている当の建物が浮き上がる」矛盾もなくなった。
- **線を直線に**: ベジェの反りを廃止。実測で直線からのズレは 0.03〜0.07px。
- **破線のサイズを均一に**: 奥へ向かって細くなる先細りをやめ、長さ8px・太さ2.6px で統一（実測でも全マーク同値）。
- **線がマーカーに被らないように**: マーカーの**画面上の半径**をシーン側で計測して配信する仕組みを追加（スプライトはワールドサイズ固定だが画面サイズはカメラ距離で変わるため、DOM 側では計算できない）。線はその半径＋8pxの余白を残して終端する。
- **検証**: 建物のホバーが無反応、マーカーのホバーでカーソルが `pointer`、マーカーのクリックでセクションがフォーカスされることを実測で確認。

### ズーム中の表示を1エリアに絞る
- **他のマーカーを消す**: エリアにズームしている間、そのエリア以外のマーカーはサイズ0へ補間して消える。カメラが今離れたばかりの場所への移動を提案し続ける状態を解消。消えたマーカーは `visible = false` にしてホバー／クリックも受け付けなくする（見えないスプライトが当たり判定だけ残る事故を防ぐ）。
- **ハイライトと線の接続先を修正**: マーカーの強調色と点線の接続先が `facing`（＝方位角から導出）のままだったため、**ズーム中は「ズーム直前に正面だったエリア」を指していた**。カードは `activeSection ?? facing` を見ていたので、カードだけ正しく他がズレる状態だった。
  - `spotlight = activeSection ?? facing` を1つ定義し、**強調色・サイズ・非表示判定・線の接続先・カード**のすべてがこれを参照するよう統一。
- **検証**: マーカーをクリック → カード・ナビタブ・強調マーカーの3つが同じエリア（経歴・活動）を指し、他のマーカーは消え、点線はその1つに繋がることをスクリーンショットで確認。

### 詳細ページを閉じた直後にカードと線が一つ前のエリアを指すバグ
- **症状**: 正面ではない別のマーカーをタップ→ズーム→詳細ページを開く→スライドで閉じる、という流れの直後、**約0.5秒だけカードと点線が「一つ前に見ていたエリア」を指し**、その後に正しい表示へ切り替わる。
- **原因**: `facing`（＝カメラが今どのエリアを向いているか）は `useFrame` のアイドル処理でしか更新されない。閉じた直後はホームへの**飛行中**で、飛行中は早期リターンするため更新が走らない。よって飛行が終わるまで**ズーム前の古い値**が残り、それを読んでいるカードと点線が古いエリアを指していた。0.5秒という長さは飛行時間そのもの。
- **修正**: カメラの行き先を決めるのと**同じ場所で `facing` も決める**ようにした。スクロールで離脱する時はそのエリア、ロゴでリセットする時は `facingSection(HOME_ANGLE)` を即座にセットする。カメラの目的地と表示が同じ判断から導かれるので、飛行中もズレない。
- **検証**: 正面と異なるセクションを開いて閉じる手順で、全サンプル（14点、5秒間）が正しいエリアを指すことを確認。**修正を外すと同じテストで11サンプルが古いエリアを指す**ことも確認済み（＝テストがこのバグを実際に検出している）。

### 点線とマーカーの間の隙間
- **症状**: 線のマーカー側の端に隙間が空く。
- **原因**: 破線をカード側から等間隔に並べていたため、**割り切れない余りがマーカー側に溜まっていた**。実測すると隙間は一定ではなく、カメラの動きに応じて **14〜34px** の範囲で伸縮していた（意図した `MARKER_GAP` は8pxのみ）。
- **修正**: 並べる基準をマーカー側に変更。余りはカード側に寄るが、そちらはカードの角に隠れて見えない。これで隙間は常に `MARKER_GAP` ちょうどになる。あわせて `MARKER_GAP` を 8px → 3px に縮め、接しているように見せつつ衝突には見えない距離にした。
- **検証**: 末端の破線の位置が20pxの倍数ではなく連続的に変化する（＝マーカー側を基準に並んでいる）ことを実測で確認。
