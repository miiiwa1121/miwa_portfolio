### 報告された3つの不具合を修正
- **開く時のカクつき**: 計測の結果、原因は2つ。
  - Skills を開くと `cdn.jsdelivr.net` へ **28リクエスト**。各スキルは最初からローカルの react-icons を持っていたのに、リモートURLが優先されていた。→ 28 → 0。
  - Products の画像が **16MB の生 PNG**（`imadoko.png` は 6.8MB / 3420px を高さ192pxのカードに表示）。静的エクスポートのため `next/image` は `unoptimized` 強制でリサイズが効かない。sharp で 1600px / WebP へ再エンコードし **16MB → 337KB（97.9%減）**。
- **戻る境界の曖昧さ**: スペーサーが 150vh、ビューポートが 100vh。パネルが画面から消えるのは progress 0.67 の時点で、**残り半画面ぶんが死に区間**だった。スペーサーを1ビューポートに揃え「消える瞬間＝戻る瞬間」を一致させた。慣性で数px手前に止まると二度とイベントが来ないため閾値 0.98、開いた直後のロックは 1200ms → 450ms。
- **視点が2〜3回切り替わる**: `camera-controls` の `_createOnRestPromise` は呼び出しの識別子を持たず、次の `rest` で誰の Promise も解決する。2つの effect が1個の boolean を共有していたため、古い飛行の `.then` が飛行中にフラグを倒し、`useFrame` が毎フレーム上書きを始めていた（1台のカメラに2人の書き手）。飛行ごとにトークンを発行して解決。あわせて、タブ切替時に「ホームの角度」を建物視点の角度で上書きしていたバグも修正。

### カメラモデルの作り直し（参考サイトの記事に基づく）
- 開発者本人の解説記事を読み、以下が判明。
  - **層の分け方**: 拍動する円形アイコンは WebGL（他の3Dオブジェクトに隠れる）、点線コネクタは DOM、ツールチップは DOM 最前面。
  - **スクロール同期のカメラパスは一度作って断念**（3D酔いの懸念）。最終形は単純な周回。
  - **FPSガバナー**: 操作中60fps / 静止30fps / **canvas がコンテンツの裏に隠れている時 0.5〜1fps**。
- **スクロール連動補間を削除**: 白い不透明パネルの裏で毎フレーム `lerpLookAt` を回していた。誰にも見えず、かつ「分岐は state・入力は ref」の時間差により視点バグの原因そのものだった。
- **FPSガバナー実装**: パネルが画面を覆いきってから `frameloop="demand"` + 1秒ハートビート。実測（WebGLドローコール計測）で覆われている間 **毎秒1描画に固定**、スペーサーで復帰することを確認。
- **慣性の流入を遮断**: 強くフリックして閉じるとカメラが回り出す症状。慣性スクロールは指を離した後も1〜2秒イベントを出し続け、ロック解除直後の残りが回転に化けていた。「ロック中に始まったストリームは、ホイールが静かになるまで受け付けない」方式で解決。
- **戻り先の仕様変更**: 「離れた時の角度を記憶して戻る」を廃止。スクロールで離脱 → **全景の距離のまま、そのエリアが正面に来る角度へ**。ロゴ/HOME → 毎回同じ固定視点。カメラの行き先を決める処理を1つの effect に統合。

### カードとマーカー
- **カードをカメラから導出**: `activeSection` 依存をやめ、周回の方位角から「今どのエリアが正面か」を求めて表示。カードがカメラを動かし、カメラがカードを変える双方向は必ず喧嘩するため一方向にした。実測で、周回に従いカードが順に切り替わること、技術スタックをスクロールで閉じた直後に「技術スタック」カードが出ることを確認。
- **エリアマーカー**: 各エリア上空に脈打つドットをスプライトで配置。深度バッファに乗るため建物が手前にあれば自然に隠れる。正面のドットはアクセントカラーで拡大。アンカー高さは現行の建物実寸に合わせた手調整値（モデル変更時に要調整）。

### カード → マーカーの点線（DOM）
- **層の分担**: マーカーは WebGL（建物に隠れてほしい）、点線は DOM（常に最前面の平面）。参考サイトの記事と同じ分け方。
- **毎フレームの受け渡しを React state に通さない**: シーンが持つカメラ情報を DOM 側が必要とするが、state 経由にすると60回/秒の再レンダーが走り、描画と同じメインスレッドを奪い合う。小さな購読チャンネル（`3d/markerScreen.ts`）を作り、シーンが push、線側は SVG の属性を直接書き換える方式にした。
- **描画**: 20個の `<circle>` をカードの角からマーカーまで二次ベジェ上に配置。半径を 4.5px → 1.8px へ先細りさせ、弦に対して垂直方向に少し反らせて弧にしている。
- **可視判定**: 当初はカメラ前後（`z < 1`）しか見ておらず、マーカーが画面上端の外（実測 y = -238）に出ると線が画面外へ飛んでいた。ビューポート内かどうかも条件に追加。

- **判明した制約**: 全周を回して実測したところ、**5エリア中「制作実績」だけ点線が常に非表示**。ピンクタワーが高く、マーカーがホーム視点の画面上端より上に出るため。マーカー高さを 13.3 → 10.4（アンテナではなく塔屋を基準）に下げても解消せず、**原因はマーカーではなくホーム視点の画角そのもの**（現在の `HOME_RADIUS = 24` では高い建物が上で見切れている）と確定。次の A1（`fitToBox` によるエリア単位の構図決定）で対応する。

### ホーム視点の画角を実測から決め直し
- **実測**: シーンに一時的な計測コンポーネントを差し込み、ワールドと各エリアのバウンディングボックスを取得。
  - ワールド全体 y -7.3 〜 22.3（上限は紙吹雪と雲で、構図の制約にすべきでない）、XZ はおよそ ±14。
  - 建物の高さ: 制作実績 **12.2**（アンテナ先端）、技術スタック 7.5、自己紹介/お問い合わせ 4.6、経歴・活動 3.8。
- **原因の特定**: 従来はカメラ高さ11・注視点 y=1 で、俯角 22.6°。垂直画角45°に対し**視野の上端が水平から0.1°**しかなく、カメラの目線より高いものは原理的に写らない。ピンクタワー(12.2)は必ず切れていた。
- **修正**: 注視点を地面(y=1)ではなく**コンテンツの中央(y=3.5)**へ。俯角16.1°となり塔が収まる。半径は 24 → 26。角度計算をスクリプトで検証してから適用した。
- **初回マウントでホーム構図が適用されていなかった**: `<Canvas camera>` は位置しか設定できず注視点は原点のままだったため、起動直後は上記の修正前より悪い俯角で回っていた。マウント時にトランジションなしでホーム構図へスナップするよう修正。
- **マーカー高さの手調整を廃止**: 建物の実バウンディングボックスの上端＋クリアランスで実行時に決める方式へ。建物が育っても屋根に埋まらない。
- **結果**: 全周を実測し、**5エリアすべてで点線が表示**されることを確認（従来は制作実績のみ常時非表示）。

### エリア単位の構図をサイズから計算（`fitToBox` は使えなかった）
- **`fitToBox` を採用しようとして撤回**: 実装を読むと冒頭で `roundToStep(theta, PI_HALF)` によりカメラ角度を90°刻みに丸め、正面・真横・真上のいずれかへスナップする。ジオラマの斜め俯瞰が壊れるため使用不可。API の説明だけを見て推奨したのは誤りだった。
- **代替として自前の純粋関数を用意**:
  - `frameDistance(radius, fov, aspect)`: 対象の外接球が収まる距離。垂直・水平の**狭い方**の半画角で計算するため、縦長ビューポートでも収まる。従来は全建物が距離13固定で、12単位のタワーと4単位の図書館が同じ扱いだった。
  - `framePose(target, azimuth, distance, tilt, sideways)`: そのエリア固有の方位角から、指定距離・俯角で見る配置を返す。`sideways` は注視点を横へずらすもので、**被写体を画面右へ寄せて左のカードを避ける**。
  - `aimOffset(distance, fov, aspect, share)`: 避ける量を「フレーム幅の何割か」から算出。距離が変われば必要量も変わるため定数では足りない。
- **検証**: 変異テスト2種（`sin` → `tan` の定番ミス、狭い方ではなく広い方の半画角を使う）で「被写体が実際に画角に収まる」テストが落ちることを確認。テスト計86件。

### カードのジェスチャ（A5）
- **タップで詳細ページ、上下スワイプで隣のスポットへ回転**。
- **既存のジェスチャとの衝突を回避**: キャンバス側はタッチの縦スワイプをカメラ回転に割り当てているため、カードがその操作を専有する必要がある。`Scene` の `isInteractive()` が `[data-ui]` を除外する設計になっていたので、カードに `data-ui` を付けるだけで解決した。
- **タップとドラッグの判別**: 移動量10px未満をタップ、縦44px以上かつ横移動より大きい場合をスワイプとする閾値方式。
- **「隣」の定義**: `SECTIONS` はオブジェクトのキー順であって周回順ではない。**方位角でソートした順序**（`SECTIONS_BY_AZIMUTH`）を用意し、`adjacentSection()` で前後に1つ進む形にした。端を越えたら反対側へ回り込む。
- **回転の指示**: 既存の周回ターゲット角を書き換えるだけ。カメラは慣性付きでそこへ寄っていき、カードは角度から導出されているので自動的に追従する（新たな同期処理は不要）。

### 描画の軽量化（B）
- **マテリアル**: `meshStandardMaterial` → `meshLambertMaterial`。ボクセルは一様なマット色で metalness / roughness の変化を表現していないため、物理ベースの計算は誰も使わない応答を計算していた。参考サイトの開発者も実測の末に同じ材質へ行き着いている。
- **シャドウマップ**: 2048 → 1024。ブロック状の形状が落とす大きく柔らかい影なので、解像度は見えない精細さのために4倍のコストを払っていた。
- **実測**: フレーム間隔の中央値 **755ms → 571ms**（1.31fps → 1.75fps、約25%の軽量化）。ソフトウェアレンダリング環境での絶対値なので実機とは異なるが、シェーディングと影パスのコスト削減自体は実在する。見た目はスクリーンショットで確認し、パステルの質感は維持されている。

### マーカーのホバー／タップ、点線の可変本数と破線化
- **マーカーにホバーとクリックを追加**: ホバーで拡大＋カーソル変更、クリックでそのエリアへ寄る（建物クリックと同じ着地点）。
- **点線を可変本数・等間隔に**: 従来は固定20個だったため、マーカーが遠いと間隔が伸び、近いと詰まっていた。曲線を細かくサンプリングして**弧長**を積算し、一定間隔（20px）で配置する方式へ。本数は長さから決まる（実測で6〜23本、間隔は 20px ±0.1px で一定）。ベジェのパラメータを等分すると曲がり部分で詰まるため、弧長で歩く必要がある。
- **デザインを円から破線へ**: 各マークを曲線の接線方向に沿った短い線分にした。奥に向かって長さと太さが細くなる。

- **その過程で重大なバグを発見**: **キャンバスがポインタイベントを一切受け取っていなかった。**
  - `elementFromPoint()` でシーンの上を叩くと `CANVAS` ではなく `MAIN` が返っていた。キャンバスのラッパーが `-z-10` で `<main>` の下に潜っていたため。
  - つまり `ProceduralObjects` の `Anchor` に実装されていた**建物のホバー／クリックは、ずっと死んでいた**（7月のログには動作確認済みと書かれているが、実際にキャンバスをクリックする検証ではなかったと思われる）。
  - `-z-10` → `z-0` に変更して解消。上に乗る要素はそれぞれ自前の z-index を持っているため影響なし。修正後、シーン上のホバーでカーソルが `pointer` になり、マーカーのクリックでセクションがフォーカスされることを実測で確認。
- **役割と docs 運用を明文化（追記）**: 「開発して終わり」にならないよう、`CLAUDE.md` に「あなたの役割はプロダクト開発 ＋ docs 作成」を明記した。あわせて devlog だけだった更新ルールを **docs 全体**へ広げ、`devlog` / `tech.md` / `voxel-object-creation.md` / `README.md` / `CLAUDE.md` のどれをいつ更新するかを表にした。devlog は毎回、他は変更の中身に応じて。

### マーカーと点線の調整
- **建物側の操作を撤去**: ホバーの浮上とクリックを削除し、建物は完全に固定。操作対象はマーカーのみとした。1つの行き先に当たり判定が2つある状態を解消し、あわせて「マーカーが乗っている当の建物が浮き上がる」矛盾もなくなった。
- **線を直線に**: ベジェの反りを廃止。実測で直線からのズレは 0.03〜0.07px。
- **破線のサイズを均一に**: 奥へ向かって細くなる先細りをやめ、長さ8px・太さ2.6px で統一（実測でも全マーク同値）。
- **線がマーカーに被らないように**: マーカーの**画面上の半径**をシーン側で計測して配信する仕組みを追加（スプライトはワールドサイズ固定だが画面サイズはカメラ距離で変わるため、DOM 側では計算できない）。線はその半径＋8pxの余白を残して終端する。
- **検証**: 建物のホバーが無反応、マーカーのホバーでカーソルが `pointer`、マーカーのクリックでセクションがフォーカスされることを実測で確認。

### ズーム中の表示を1エリアに絞る
- **他のマーカーを消す**: エリアにズームしている間、そのエリア以外のマーカーはサイズ0へ補間して消える。カメラが今離れたばかりの場所への移動を提案し続ける状態を解消。消えたマーカーは `visible = false` にしてホバー／クリックも受け付けなくする（見えないスプライトが当たり判定だけ残る事故を防ぐ）。
- **ハイライトと線の接続先を修正**: マーカーの強調色と点線の接続先が `facing`（＝方位角から導出）のままだったため、**ズーム中は「ズーム直前に正面だったエリア」を指していた**。カードは `activeSection ?? facing` を見ていたので、カードだけ正しく他がズレる状態だった。
  - `spotlight = activeSection ?? facing` を1つ定義し、**強調色・サイズ・非表示判定・線の接続先・カード**のすべてがこれを参照するよう統一。
- **検証**: マーカーをクリック → カード・ナビタブ・強調マーカーの3つが同じエリア（経歴・活動）を指し、他のマーカーは消え、点線はその1つに繋がることをスクリーンショットで確認。

### 詳細ページを閉じた直後にカードと線が一つ前のエリアを指すバグ
- **症状**: 正面ではない別のマーカーをタップ→ズーム→詳細ページを開く→スライドで閉じる、という流れの直後、**約0.5秒だけカードと点線が「一つ前に見ていたエリア」を指し**、その後に正しい表示へ切り替わる。
- **原因**: `facing`（＝カメラが今どのエリアを向いているか）は `useFrame` のアイドル処理でしか更新されない。閉じた直後はホームへの**飛行中**で、飛行中は早期リターンするため更新が走らない。よって飛行が終わるまで**ズーム前の古い値**が残り、それを読んでいるカードと点線が古いエリアを指していた。0.5秒という長さは飛行時間そのもの。
- **修正**: カメラの行き先を決めるのと**同じ場所で `facing` も決める**ようにした。スクロールで離脱する時はそのエリア、ロゴでリセットする時は `facingSection(HOME_ANGLE)` を即座にセットする。カメラの目的地と表示が同じ判断から導かれるので、飛行中もズレない。
- **検証**: 正面と異なるセクションを開いて閉じる手順で、全サンプル（14点、5秒間）が正しいエリアを指すことを確認。**修正を外すと同じテストで11サンプルが古いエリアを指す**ことも確認済み（＝テストがこのバグを実際に検出している）。

### 点線とマーカーの間の隙間
- **症状**: 線のマーカー側の端に隙間が空く。
- **原因**: 破線をカード側から等間隔に並べていたため、**割り切れない余りがマーカー側に溜まっていた**。実測すると隙間は一定ではなく、カメラの動きに応じて **14〜34px** の範囲で伸縮していた（意図した `MARKER_GAP` は8pxのみ）。
- **修正**: 並べる基準をマーカー側に変更。余りはカード側に寄るが、そちらはカードの角に隠れて見えない。これで隙間は常に `MARKER_GAP` ちょうどになる。あわせて `MARKER_GAP` を 8px → 3px に縮め、接しているように見せつつ衝突には見えない距離にした。
- **検証**: 末端の破線の位置が20pxの倍数ではなく連続的に変化する（＝マーカー側を基準に並んでいる）ことを実測で確認。

### 高速回転時に線がマーカーに繋がっていないように見える件
- **切り分け**: まず「線が配信された位置に正しく届いているか」を計測。ドラッグ中の全サンプルで**誤差0px**だった（線の描画側は正しい）。
- **真因**: 高速回転中は正面エリアの判定が毎フレーム切り替わり、線の接続先が画面の端から端へ飛ぶ。一方**マーカーの色とサイズは 0.4 秒かけて補間**されるため、線が指す先はまだ小さく白いままで、大きくオレンジの点は別の場所に残る。これが「繋がっていない」に見えていた。
- **対処1（検証済み）**: **正面のマーカーだけは補間せず即座に確定**させる。線が指し始めた瞬間から、その点は既に正しい見た目になっている。降格する側は引き続き補間する（そちらには何も繋がっていないため）。ドラッグ中のキャプチャで、線が常にフルサイズ・アクセント色の点に終端することを確認。
- **対処2（この環境では検証不能）**: 角速度が一定以下になるまで正面判定を保留するヒステリシスを追加（`FACING_SETTLE_SPEED = 1.0 rad/s`）。高速フリック中にカードが4エリアを高速で行き来する問題への対処だが、**この環境は約1.7fpsでフレーム間隔が0.6秒あり、実機60fpsのフリック（約30rad/s）が0.8rad/s程度に見えてしまうため発火条件を再現できない**。実機での確認をお願いしたい。

### 点線の両端を固定
- **症状**: 前回マーカー側を基準に並べ替えた結果、余りがカード側に寄り、**線がカードの裏に出入りするようになった**（潜り込む量が距離に応じて変動する）。
- **どちらか一方を基準にする限り、もう一方に余りが出る**という構造だった。カード基準ならマーカー側の隙間が14〜34pxで変動し、マーカー基準ならカード側が潜り込む。
- **対処**: 両端を固定し、**間隔側で余りを吸収**する方式へ。最初の破線はカードの角ちょうど、最後の破線はマーカーの3px手前で終わり、間隔は `DASH_SPACING` の±半歩以内に収まる。
- **実測**: カード側の端は0.0〜0.1pxで不動、間隔は18.8〜21.9px（設定値20px）。
  - 1サンプルだけ不揃いな値が出たが、これは計測側が**属性の書き換え途中を読んだ**もの。書き換えは `useFrame` 内で同期的に完了するためブラウザが中間状態を描画することはなく、画面上には現れない。

### 点線のレイアウトを reference 方式に戻す
- **参考動画（`reference/video4.mov`、MP4へ変換して28フレームを抽出）から判明したこと**:
  - カード側の点は**完全に静止**しており、シーンが回っても1pxも動かない。
  - 点の増減と余りは**すべてマーカー側**で吸収されている。実際、reference の終端の隙間は 52〜85px と大きく変動しているが問題になっていない。
  - カードの角には**点が1つ描かれており**、そこから少し離れて線が始まる（線はカードの裏に入らない）。
- **前回の実装の誤り**: 「両端を固定し間隔で余りを吸収」した結果、本数が変わるたびに**全部の点が少しずつずれて**いた。カード側が静止していなかった。
- **修正**: カード側から**固定間隔20px**で並べ、余りは終端に残す方式へ戻した。カードの角の点は SVG ではなく**カード自身の要素**にした（SVGオーバーレイはクロームより下のレイヤーにあり、カードの裏に隠れて見えないため。reference も `index-card-circle` としてカード側に持っている）。線の開始位置もカードの外側にずらし、裏に潜り込まないようにした。
- **実測**: カードに最も近い3つの破線が、本数が4〜21と変わっても常に **30, 50, 70px** の位置で不動であることを確認。

### 線のデザインを三角ギザギザ（^^^^^^^）へ
- 72本の `<line>` を **1本の `<polyline>`** に置き換え。頂点を交互に「基準線上」「基準線から垂直に6px」へ置くことで `^^^^` の形にしている（左右対称の波ではなく、谷が基準線に乗る形）。
- **カード側が動かない性質は維持**: 頂点の間隔（11px）は固定で、カード端から数えて配置する。余りと頂点の増減は終端側で吸収する。
- 頂点数を偶数に揃え、**最後の頂点が必ず基準線上**に来るようにした。奇数だと線がマーカーの脇を向いて終わってしまうため。
- **実測**: カードからの開始位置は 26.0px で不動、偶数頂点のオフセットは ±0.1px（＝基準線上）、奇数頂点は 6.0px、辺の長さは 12.5px（= √(11²+6²)）。頂点数は距離に応じて13〜45と変動。

### 線の伸縮が「1文字ずつ」になる問題
- **症状**: 線の長さが変わるとき、山1つ分がまとめて現れたり消えたりする。
- **原因**: 頂点数を `Math.floor()` で整数に切り捨てていたため、11px単位でしか伸縮できなかった。さらに「最後の頂点を基準線上に揃える」ために偶数へ丸めていたので、実際には**22px（山1つ分）刻み**で増減していた。
- **対処**: 整数の頂点までを打った後、**最後に実距離ちょうどの頂点を補間して追加**する。末端は連続的に滑り、途中で整数頂点を通過するだけなので段差が出ない。
  - 副次的な改善として、末端が常に `reach` ちょうどで終わるため、**マーカーとの隙間が常に `MARKER_GAP` 固定**になった（従来は最大22pxばらついていた）。
  - トレードオフとして、末端の頂点は基準線上とは限らず、最大6px（振幅ぶん）横にずれる。実機では判別できない差。
- **実測**: 末端の距離を16回サンプルし、`(距離 - 26) mod 11` が 1.2〜11 に分散することを確認（すべて0なら整数刻みのまま）。

- **症状**: カード側の接着点は回転しても動かないのに、**点（マーカー）側だけ回転で接着位置がズレる**。
- **原因**: 前回「実距離ちょうどの頂点を補間して追加」したときに残したトレードオフそのもの。末端の頂点は `reach` の距離にはあるが、ギザギザの途中の高さ（0〜6px）を補間して置いていたため、**基準線から最大6.0px横に振れていた**。点までの実距離も `MARKER_GAP` と `√(MARKER_GAP²+6²)` の間で揺れる。「実機では判別できない」と書いたが、回転させ続けると末端だけが小刻みに揺れて見える。
- **対処**: 頂点の並べ方を「半歩（11px）単位」から**「1山（22px）単位」**に変え、**両端とも基準線上に固定**した。カード側は従来どおり `CARD_GAP` ちょうど、点側は `reach` ちょうど。
- **余りの吸収先**: 山1つ分に満たない端数は、**最後の山だけが引き受ける**。端数の中点に頂点を1つ置き、その高さを `6px × 端数 / 22px` で伸ばす。端数が22pxに達した瞬間の形は通常の山と完全に一致するので、`cycles` が1つ増えて端数が0に戻っても**形が飛ばない**（前回の「1文字ずつ」問題を再発させない）。
- 却下した案: 末端の頂点だけ高さを0に落とす。端数が小さいときに幅0の針のような突起が出る。
- **実測**（純関数を切り出して `reach` を 74〜900px まで 0.05px 刻みで走査）:
  - 修正前の末端の横ズレ **最大6.00px**、あるべき位置（`reach`・基準線上）からの距離 **最大6.02px** → 修正後は**両端とも 0.00px**。
  - 形の連続性: `reach` を0.1px動かしたときのポリライン同士のハウスドルフ距離が **最大0.23px**（頂点数が変わる境界を含む全域）。頂点index同士で比べると本数変化のせいで22pxの偽の段差が出るので、この指標で測った。

### 回転を全体的に穏やかにする
- スクロール1単位あたりの回転量 `WHEEL_SENSITIVITY` を **0.0008 → 0.0004 rad**（半分）、放置時の自動回転 `AUTO_ORBIT_SPEED` を **0.045 → 0.022 rad/s**（約半分）へ。1周にかかる時間は **2分20秒 → 4分46秒**。
- ドラッグの `DRAG_SENSITIVITY`（0.004 rad/px）は**据え置き**。指の動きに直接ついてくる操作なので、弱めると重く感じる方向にしか効かない。指示は「スクロール」と「自動回転」だったので触っていない。
- `FACING_SETTLE_SPEED`（正面のエリアを切り替えてよい回転速度の上限 1.0 rad/s）は変更不要。自動回転が遅くなったぶん余裕がむしろ広がる。コメント内の実測値だけ追随させた。
- **計測方法**: 角度を直接読む手段がない（`CameraControls` は window に出していない）ので、**カードの見出しが切り替わる時刻**から逆算した。各エリアの方位角は建物座標の `atan2(x, z)` で決まり、境界は隣り合う方位角の中点。
  - 自動回転: 無操作で放置し、`Tech Stack` 23.2s → `Works` 64.3s → `Get in touch` 115.8s。**51.6°の移動に41.1秒＝0.0219 rad/s**（設定値 0.022、旧値なら20秒）。
  - スクロール: deltaY 合計3200を流し、`Journey`(45°) から `Tech Stack`(基本域 83.4〜135°) へ。**回転量73°＝新しい係数**（旧係数なら147°回って `Works` の域に入る）。
- **罠**: 最初の計測でスクロール直後に読んだカードが `Journey` のままで「効いていない」と誤読しかけた。`FACING_SETTLE_SPEED` が**回転が収まるまで正面エリアの切り替えを保留する**ため、ダンピングが落ち着く数秒後にようやく `Tech Stack` へ変わる。この種の計測では**カードは常に数秒遅れる**前提で待つこと。
  - ついでに判明したこと: スクロールの回転方向は `targetAngleRef -= deltaY * 係数` の見た目に反して**方位角が増える向き**に動く。`CameraControls` の `azimuthAngle` と `atan2(x, z)` の向きが逆であるため（`Scene.tsx` のドラッグ側コメントにある通り）。

### 停止・再生ボタン（ジオラマを丸ごと止める）
- **要件**: JPトグルの横にボタンを置き、押した**その瞬間**に自動回転とオブジェクトの動きを全部止める。
- **設計**: 各コンポーネントに一時停止の分岐を配るのではなく、**ジオラマ専用の時計 `3d/sceneClock.ts` を1つ置き、動くものは全部そこから時刻を読む**方式にした。観覧車・トラム・雲・住人・紙吹雪・マーカーの脈動・アイドル自動回転が、フラグ1つで同じフレームに止まる。
  - `time(elapsed)` は停止中は凍結した値を返し、`delta(realDelta)` は停止中0を返す。`clock.elapsedTime` を直接読んでいた箇所をこの2つに置き換えただけで、追加の状態は各コンポーネントに1つも増えていない。
  - React state にはしていない。`useFrame` の中から毎フレーム読むため（`markerScreen.ts` と同じ理由）。
- **停止中も手で回せる**ようにした。「自動で流れていくのを止めて、自分の見たい角度でじっくり眺める」がこのボタンの用途なので、ドラッグまで殺すと目的を外す。ダンピングには実 delta を渡し、自動回転の加算だけ `sceneClock.delta()` を通している。
- **惰性も切る**: 押した瞬間、進行中の flight がなければ回転ターゲットを現在の方位角に落とす。これがないとダンピングの残りぶんだけ押した後もぬるっと動き続ける。flight 中は除外（ターゲットは飛行先なので、上書きすると着地後に建物から引き戻される）。
- **一時停止ぶんは「割り引く」**（時刻をリセットしない）。トラムと住人は位置が時刻だけの関数なので、素朴に実時間へ戻すと**停止していた時間ぶん island を瞬間移動する**。
- **却下した案**:
  - R3F の `clock` 自体を止める / `frameloop="never"`。delta が0になるのでダンピングも死に、停止中に手で回せなくなる。
  - 毎フレーム `t += delta` で積算する。**`useFrame` の購読順に依存**して1フレームずれる。順序を保証する `priority` は、0以外を使うと R3F が自動描画をやめてしまうため使えない。オフセット方式なら順序非依存になる。
- **計測**（実ブラウザ、トラムの角度を一時的に `window` へ出して直接読んだ）:

  | 場面 | 正しい実装 | 割引をやめた対照実験 |
  | --- | --- | --- |
  | 通常時 1.0秒 | +0.2427 rad（設計値 0.22 rad/s） | — |
  | 停止して 5.02秒 | **+0.0000 rad** | +0.0000 rad |
  | 再生後 1.14秒 | **+0.2506 rad**（= 1.14 × 0.22、連続） | **+1.4733 rad**（70°の瞬間移動） |

  - 画面全体でも、**10秒停止して変化ピクセル 0.000%**（完全静止）。停止中にドラッグした後3秒放置しても 0.034%（惰性で流れ続けていない）。
  - 純粋ロジック側は `sceneClock.test.ts` で9件。**変異テスト5種（凍結の無視・割引の上書き・停止/再生それぞれの冪等性の破壊・delta の素通し）すべてが落ちる**ことを確認。
- **罠1**: 「再生後200ms」を見て「再生されていない」と誤読しかけた。**ヘッドレスの SwiftShader は約2fps** しか出ておらず、200ms ではフレームが1枚も進んでいない。この環境での時間依存の計測は、**フレーム番号も一緒に出して**進んだことを確かめてから読む。
- **罠2**: 最初「変化ピクセルの割合」で跳びを検出しようとしたが、**この指標は飽和する**。カメラがごく僅かに動くだけで画素の25〜30%が変わるため、200msの通常移動（28.7%）と5秒ぶんの瞬間移動（26.4%）が区別できない。跳びの検出には**対象の位置そのもの**を測る必要があった。

### 点との隙間が開いたり詰まったりする（スプライトの画面サイズの見積もり方が誤り）

- **症状**: 回転させると、線の末端と点の隙間が広がったり狭まったりする。カード側は動かないのに点側だけ落ち着かない。
- **前回までの認識が間違っていた**。「末端は常に `reach` ちょうどで終わるので隙間は `MARKER_GAP` 固定」と書いたが、固定なのは**点の中心からの距離**であって、**点の縁からの距離**ではない。差は `radius`（点の画面半径）で、その `radius` の求め方が誤っていた。
- **原因**: マーカーの画面半径を、**ワールド座標の鉛直ベクトルを射影して**測っていた。

  ```ts
  projectedEdge.copy(anchor).addScaledVector(state.camera.up, worldRadius).project(camera)
  ```

  スプライトはビルボードで、three.js は頂点を**ビュー空間で**ずらす（`sprite.glsl.js` の `mvPosition.xy += rotatedPosition`）。つまり画面サイズは `scale × (viewportHeight / (2 tan(fov/2) × ビュー深度))` だけで決まり、カメラの俯角にも画面内の位置にも一切依存しない。一方ワールド鉛直の射影は、
  1. 俯角ぶん foreshorten され（`cos φ` 倍）、
  2. 遠近法で画面の上下端に向かうほど伸縮する（`ndcY · tan(fov/2) · sin φ` の項）。

  2つめが効く。**マーカーは回転につれて画面を上下に動く**ので、見積もりが画面位置に連動して振れる。さらに、この式はスプライトの矩形全体を測っていて、テクスチャに描かれた円は矩形の 0.37 しか占めていない。
- **対処（仕組みの作り直し）**: 見積もる方向を逆にした。**点の大きさを「画面上の px」で先に決め、それを実現するワールド scale を毎フレーム逆算する。**
  - `worldLayout.ts` に純関数 `pixelsPerWorldUnit()` / `markerScaleForScreenRadius()` を追加。テクスチャの充填率 `MARKER_DOT_FILL = 0.37` も同じ場所に置き、テクスチャを描く側もこの定数から円の半径と縁の太さを導く（＝縁の一番外側の画素がちょうど 0.37 に来る）。
  - `AreaMarkers` は各スプライトの**ビュー深度**（`matrixWorldInverse` を掛けた `-z`。カメラからの直線距離ではない）から scale を決め、**実際に描いた px 半径をそのまま publish** する。推定値ではなく確定値になった。
  - 大きさの指定も world 単位（0.5 / 0.8 / 1.05）から px（9 / 14 / 18）に変えた。ホーム視点での見た目はほぼ同じで、寄ったときに点が膨らまなくなる。
- **なぜ画面 px で持つのが正しいか**: 線は DOM の SVG で、線幅 2.4px・ギザギザの間隔 11px と**画面 px で組まれている**。その線が指す先の点だけを world 単位で持ち、毎フレーム px に「戻す」から誤差が入る。注釈の両端を同じ単位で持てば、戻す計算自体が消える。
- **ついでに直した2点**:
  - 線のカード側の起点を、カードの矩形からの手計算（`rect.right - 20`）ではなく**アンカーの点そのものの要素**を測る形にした（`page.tsx` の `<span>` に ref）。従来は点の**右上角**を起点にしていて中心と 4.5px ずれていた。両端とも「点の縁から一定距離」で揃う。
  - `publishMarkerScreen` の整数丸めをやめた。1フレームあたり最大0.5pxの震えを生んでいたうえ、自動回転で毎フレーム値は変わるので節約にもなっていない。停止中は値が完全に一致するので早期 return は従来どおり効く。
- **計測**（自動回転で放置し45サンプル。`window.__marker` に1フレームぶんの状態を出して、スクショとDOM読みの時差を挟まずに測った）:

  | | 修正後 | 旧式（同じ実行内で並行計算） |
  | --- | --- | --- |
  | 点の縁までの隙間 | **10.15〜10.24px（振れ幅 0.09px）** | 14.00〜17.15px（振れ幅 **3.15px**） |
  | カード側の隙間 | 18.14〜18.25px（振れ幅 0.11px） | 同左（もともと安定） |

  - 旧式の誤差が画面位置に連動することも数字に出た。マーカーが画面下部（`screenY≈490`）のとき隙間 14.0〜14.5px、画面最上部（`screenY≈21`、Products の塔）のとき **15.9〜17.2px**。
  - 残る 0.09px の振れは脈動（±10%）に隙間を追従させているぶん。点の縁から一定距離を保つ側を選んだ結果で、線の末端は約±0.1px しか動かない。
  - 寄った状態でも隙間 10.20px（旧式なら 15.81px）。
- **テスト**: `worldLayout.test.ts` に9件追加。**変異テスト5種（`2*tan` の 2 を落とす／半角でなく全角の fov を使う／テクスチャ充填率を無視する／px per unit を掛け算にする／深度を非線形にする）すべてが落ちる**ことを確認。
- **罠**: ヘッドレスでの検証を最初スクショで組んだが、**この環境では `page.mouse.move` 1回ごとに数千の instanced voxel へのレイキャストが走り**、1サンプルに1分かかったうえ、スクショとDOM読みの間にカメラが60px動いて測定そのものが壊れた。入力を一切使わず**自動回転に流させて**、1フレームぶんの状態をまとめて読む形にしたら1サンプル1.5秒で済み、時差も消えた。

### 点側だけ1フレーム遅れていた（`camera-controls` は行列を更新しない）

- **症状**: 回している最中だけ、線の接着点がおかしくなる。**カメラが左→右のときは点から離れ、右→左のときは点に被さる**。止めれば正しい位置に収まる。
- **回転方向で符号が反転する**時点で、計算誤差ではありえない。1フレームぶんの遅れの符号が、動く向きで反転しているだけ。
- **原因**: `camera-controls` の `update()` は毎フレーム `position` と `quaternion` を書き換えるが、**`matrixWorld` / `matrixWorldInverse` を更新しない**。更新するのは `focalOffset` を使っている場合の分岐だけで、このシーンはそこを通らない（`camera-controls.module.js` の `update()` 末尾）。

  1フレームの中身:

  | 順番 | 何が起きるか | カメラの状態 |
  | --- | --- | --- |
  | priority -1 | drei の `controls.update()` | 座標は**今フレーム**、行列は**前フレーム** |
  | priority 0 | `AreaMarkers` の `.project(camera)` | `matrixWorldInverse` を読む＝**前フレーム**で射影 |
  | 描画 | `gl.render()` が `updateMatrixWorld()` を呼ぶ | **今フレーム**でスプライトを描画 |

  線は前フレームの点の位置へ、点は今フレームの位置へ。**決定的な1フレーム遅れ**で、静止しているカード側には現れない。
- **対処**: `AreaMarkers` の `useFrame` の冒頭で `camera.updateMatrixWorld()` を1行呼ぶ。`Camera` の同メソッドは `matrixWorldInverse` も張り直すので、以降の射影も深度計算も `gl.render()` と同じ行列を読む。コストは 4x4 の合成と逆行列が毎フレーム1回だけ。
- **前回の計測が「隙間の振れ幅 0.09px」と出ていた理由**: 発行値も半径も**同じ古い行列**から計算していたので、式としては完全に整合していた。画面とズレていることは、同一フレーム内の値どうしを比べる方法では原理的に検出できない。**「自分の計算どうしが一致する」ことと「画面と一致する」ことは別**という教訓。
- **計測**（同一フレーム内で、更新前の行列と更新後の行列の両方で同じアンカーを射影し、その距離を測った）:

  | 場面 | 射影のズレ |
  | --- | --- |
  | 放置（自動回転のみ） | 17.7〜21.3px（平均 18.9px） |
  | ホイールで回している最中 | 18.4〜**2224.2px**（平均 766.8px） |

  - ヘッドレスの SwiftShader は約2fpsなので1フレームぶんの移動量が実機より大幅に大きく出る。60fps なら放置時は 1px 未満、速く回したときに数十px という桁になる。「回している最中だけ」「速いほどひどい」という報告と一致する。
- **DOM の SVG のままでよいか**: 回転中に撮った合成済みスクリーンショット（左回り・右回り各3枚）で、線が点にきちんと接着していることを確認した。**SVG レイヤーと WebGL キャンバスは同じ合成フレームに乗る**ので、線をキャンバス側へ移す必要はない。
- **参考サイト（haru-ni.net）の確認**: 全画面の SVG は無く、`<canvas class="canvas-view-inner">` が1枚だけ（SVG は 12×20 のアイコン16個と 88×24 のロゴ3個のみ）。線もシーンと同じキャンバスに描いている。1枚のキャンバスに寄せれば、そもそもこの種のズレが構造的に起こりえない — という設計判断の実例。今回は原因が別（行列の更新漏れ）だったので採用しなかった。
- **却下した案**: 点のレイヤーを線より上げ、点の周りに透明な緩衝帯を置いて線を隠す。**症状を隠すだけで原因が残る**うえ、点は深度テスト付きの WebGL スプライト（`z-0` のキャンバス内）なので、点だけを DOM の線より前面に出すことはそもそもできない。

- **建物上のマーカー点も、自己紹介だけ自分自身を隠す**: `AreaMarkers.tsx` は元々「フォーカス中は他のマーカーが消える」実装だったが、**フォーカスした本人のマーカーは残る**仕様だった（他セクションは全画面シートの裏に隠れるので実害がなかった）。自己紹介はシートを被せないため、このままだとカードも点線もないのに建物の上にだけ点が浮く。`section === "about" && activeSection === "about"` のときだけ半径0にする1行を追加。他セクションの挙動は変えていない。
- **専用のカメラ構図**: 「カメラの行き先を決める effect は1つだけ」の不変条件を保つため、新しい effect は作らず、既存の `framePose` / `aimOffset` に**about専用の係数**を渡すだけにした（`worldLayout.ts`）。
  - `ABOUT_TILT = 0.62`（通常の `SECTION_TILT = 0.34` よりかなり深い見下ろし角）
  - `ABOUT_DISTANCE_MULTIPLIER = 2.1`（`frameDistance()` の結果を2.1倍、遠景にする）
  - `ABOUT_CARD_SHARE = 0.55`（通常の `CARD_SHARE = 0.3` より大きく右へ寄せる）
  - `Scene.tsx` の唯一のフォーカス用 effect 内で `activeSection === "about"` のときだけこの3つを使う3行の分岐のみ追加。参照サイト（`reference/image2.png`）のような「左上の遠くから見下ろす」構図になる。
- **検証**: `worldLayout.test.ts` に、`ABOUT_TILT > SECTION_TILT` 等の直接比較と、実際に `framePose`/`aimOffset` に通した結果が標準構図より「遠い・高い・より横にずれる」ことを確認するテストを追加（全体で計116件）。**変異テスト**として `ABOUT_TILT` を意図的に `SECTION_TILT` 未満の値に書き換え、追加したテストが落ちることを確認してから元に戻した。
  - ヘッドレスChrome + SwiftShaderで自己紹介タブを実際にクリックし、カード・点・点線が消えて素のテキストが左に出ること、建物が右側へ大きく引いた構図で写ることをスクリーンショットで確認（コンソールエラーなし）。続けて別セクション（技術スタック）を開いても通常どおりカード無しで全画面シートが開くことも確認し、他セクションへの影響がないことを確かめた。

### 自己紹介表示中もジオラマを回し続ける

- **要望**: 自己紹介を開くとカメラがその場に静止してしまい、ホーム画面のような「街がゆっくり回り続ける」生きた感じが失われていた。他のセクションは全画面シートが裏を覆うので静止していても気づかれないが、自己紹介はシーンがそのまま見えているため気になる。
- **単純に自動回転のガードを外すだけでは壊れる**: ホームのアイドル回転は `controls.rotateAzimuthTo()` で、**今カメラが向いている注視点を中心に**回す実装。自己紹介の構図は建物の中心そのものではなく、`aimOffset` で右にずらした点を注視点にしている（そうしないと被写体がテキストの裏に来る）。この注視点を中心にそのまま回すと、**回転の軸が建物からズレて**建物が画面の中を左右にふらつきながら回ることになる。
- **対処**: 毎フレーム `framePose()` を組み直す方式にした。飛行が着地した瞬間の `target`（建物の実バウンディング球の中心）・`distance`・`sideways` を `aboutOrbitRef` に保存しておき、方位角だけを `sceneClock.delta()` ぶん進めて再計算・`setLookAt(..., false)`（無遷移）で毎フレーム書き込む。こうすると軸は常に建物の中心のままで、右寄せの構図を保ったまま回る。ユーザー入力は自己紹介中ロック済みなので、ホーム視点のような `damp()` によるジャンプ吸収は不要（前フレームの値に単純加算するだけで滑らか）。
- **新しい effect は作らず**、カメラの行き先を決める唯一の effect（フォーカス時の分岐）で `aboutOrbitRef` を初期化し、既存の `useFrame` 内に分岐を1つ足しただけ。「行き先を決める effect は1つ」の不変条件は維持。
- **検証**: ヘッドレスChromeで自己紹介を開いたまま4秒間隔で3枚スクリーンショットを撮り、テキストの位置は不動のまま観覧車・タワー・看板が連続的に画面内を移動している（＝回転している）ことを目視確認。コンソールエラーなし。`npm test`（116件）・lintともにクリーン。

### 自己紹介の回転軸を「自己紹介の建物」から「デフォルトと同じ島の中心」へ

- **指摘**: 前回実装した自己紹介の継続回転は、`sphere.center`（自己紹介の建物自身のバウンディング球の中心）を軸に回していた。ユーザーから「回転の軸はデフォルトと同じにしたい」と指摘を受けた。実際、ホーム画面のアイドル回転は常に**島の中心**（`[0, HOME_TARGET_Y, 0]`、`HOME_RADIUS` の円周上）を軸にしており、自己紹介だけ違う軸で回っていたのは、他のすべてのビューと一貫しない挙動だった。見た目としては「島全体が自分の中心で回る」のではなく「自己紹介の小さな建物1つが静止点になり、島の残りがその周りを回る」ような回転になっていたはずで、指摘の通り。
- **対処**: `worldLayout.ts` の `ABOUT_DISTANCE_MULTIPLIER`（建物のバウンディング球ベースの距離に掛ける倍率）を廃止し、代わりに **`ABOUT_DISTANCE = HOME_RADIUS / Math.cos(ABOUT_TILT)`** を新設。ホームと同じ半径 `HOME_RADIUS` を保ったまま `ABOUT_TILT` ぶんだけ急な角度で見下ろすと、水平距離（`ABOUT_DISTANCE * cos(ABOUT_TILT)`）がちょうど `HOME_RADIUS` に一致する — 三角関数から軸と半径が導かれる形にした（数値を目視で合わせるのではなく、定義から一致することが保証される）。
  - `Scene.tsx`: フォーカス用 effect 内で、`isAbout` のときの `target` を建物のバウンディング球中心ではなく `[0, HOME_TARGET_Y, 0]`（ホームの注視点と同じ）に変更。着地後の継続回転（`aboutOrbitRef`）もこの軸をそのまま使うので、着地の瞬間から回転開始まで軸のつなぎ目が生じない。
  - 建物固有の `frameDistance()`（バウンディング球の半径から距離を出す関数）は自己紹介では使わなくなったため、`isAbout` の分岐でスキップするよう整理。
- **検証**: `worldLayout.test.ts` に核心のプロパティを直接テストする形で追加——「`ABOUT_DISTANCE * cos(ABOUT_TILT)` が `HOME_RADIUS` に一致する」「任意の方位角で `framePose([0,HOME_TARGET_Y,0], azimuth, ABOUT_DISTANCE, ABOUT_TILT)` と `homePose(azimuth)` が同じ水平距離（軸からの距離）を持つ」ことを直接検証（計118件）。**変異テスト**として `ABOUT_DISTANCE` を `HOME_RADIUS * 2.1`（旧倍率を単純適用した誤った式）に書き換え、この新しいテストが確実に落ちることを確認してから元に戻した。
  - ヘッドレスChromeで4秒間隔の3枚を再撮影し、回転が引き続き滑らかに進んでいること（`SKILLS` の看板など、以前のフレームでは見えていなかった建物が視界に入ってくる）を目視確認。コンソールエラーなし。

### 自己紹介の構図を、参考画像とのピクセル計測で合わせ込む

- **目視をやめて計測にした理由**: それまでの調整は「目視で7割くらい」といった主観だったため、参考画像（`reference/image2.png`）とどこがどれだけ違うのかを数字で出せていなかった。スクリーンショットと参考画像の**両方**を同じアルゴリズムに通し、オブジェクトのバウンディングボックスをフレームに対する%で出す計測スクリプトを書いた。
- **計測スクリプトで踏んだ罠3つ**（いずれも、素朴に書くと違う場所を測ってしまう）:
  1. **紙吹雪**: 単純な min/max のバウンディングボックスだと、画面の隅に1粒漂う4pxの紙吹雪が端を決めてしまう。列・行ごとに「オブジェクト画素の割合」を数え、閾値を超えた列/行だけを採用する密度方式にした。
  2. **文字を拾う**: 「背景色と違う画素＝オブジェクト」だと本文テキストも含まれ、左端がテキスト段の位置になる。彩度で切り分けようとしたが、**参考サイトの本文色は実測 `[66,38,18]` の濃い茶で彩度0.73**と高く、色では分離できなかった（こちらの本文は `#111827` のほぼ黒なので明度の下限で除外できる）。参考画像側は右半分にテキストが無いので、探索範囲を x>52% に限定して解決。
  3. **アスペクト比**: 参考は 3420x1904（1.796）、こちらの計測は 1600x1000（1.6）だった。同じ光景でも横に狭いフレームほど画面に占める割合は大きくなるため、**存在しない構図差を測ってしまう**。1616x900（1.796）で撮り直して比較した。
- **判明した差と対処**: 縦の寸法自体はほぼ同じ（高さ 74.3% 対 参考 75.4%）で、**問題はサイズではなく位置**だった。島が約10ポイント下にずれ、下端が 99.9%（＝画面外に見切れ）だった（参考は 90.4% で完全に収まる）。
  - `ABOUT_DISTANCE_MULTIPLIER` を廃し、**`ABOUT_RADIUS`（軌道半径）と `ABOUT_TARGET_Y`（注視点の高さ）を別々の定数に分離**。前回「回転軸をデフォルトと同じに」した際、軌道半径まで `HOME_RADIUS` に固定していたが、**共有すべきなのは軸（原点を通る垂直線）であって半径ではない**。分離しても軸は変わらないので、前回の要望は保ったまま構図だけ調整できる。
  - 注視点の高さは当て推量ではなく計算で出した。1画面ぶんの高さは `2 · ABOUT_DISTANCE · tan(fov/2)` ワールド単位、注視点の移動は画面上で `cos(ABOUT_TILT)` 倍に効く。ここから逆算した `ABOUT_TARGET_Y = -1.7` で、島の中心が**一発で 52.4%**（参考 52.7%）に入った。
- **左端を参考の 52% ぴったりには合わせなかった**: こちらの島は**平たく横に広い円盤**、参考の街は**縦に密集した塊**で、フレーム幅に占める割合が元々違うため、左端と右端を同時には一致させられない。参考が実現しているのは「オブジェクトが切れずに収まり、文字との間に余白がある」ことなので、**文字とオブジェクトの間隔**で合わせた（こちら 2.7% 対 参考 3.1%）。
- **1枚のスクショで詰めると間違える（今回いちばんの罠）**: 半径30で「右端 96.9%、余裕あり」と判断した直後、同じ設定の別スクショが「右端 99.9%」を返した。**被写体が回り続けている**ため、タワーや看板がシルエットに出入りして投影幅が振れるのが原因（実測でフレーム幅の 45.8〜50.0% と 4ポイント以上変動）。1点計測では「収まっている角度」をたまたま撮っただけになる。21秒間隔で8枚、ほぼ一周ぶんサンプリングして**最悪角度**で判断する方式に切り替え、半径を 30 → 32 にして全角度で収まるようにした。

  | | 参考画像 | 実装（最小〜最大） |

  | 左端 | 52.0% | 49.4 〜 51.2% |

### ホームの島を右に寄せ、フォーカスの切り替えを即時にする

- **要望2点**: (1) カードの反対側が空いているので、ホームの島を参考画像（`reference/image.png`）のように少し右へ寄せたい。(2) 素早くスクロールすると、フォーカス（カードの内容・強調されるドット・点線の行き先）が切り替わらない瞬間がある。
- **前提の確認**: 依頼文は「カードが右にある」だったが、カードは `page.tsx` の `flex-1 flex items-center w-full` に単独で入っているので実際は**左**、参考画像も「カード左・オブジェクト右」だった。要望された方向（右へ寄せる）と参考画像が一致しているので、左の言い間違いとして進めた。

#### 右寄せは焦点オフセット（focal offset）で

- **注視点をずらす既存の手（`framePose` の `sideways`）は使えない**。ホームのアイドル回転は `controls.rotateAzimuthTo()` で、**注視点＝公転の軸**を中心に回す。注視点を横にずらすと軸が島の中心から外れ、一周する間に島が画面上を円を描いてふらつく（自己紹介で同じ罠を踏んで、毎フレーム `framePose` を組み直すことで回避した経緯がある）。さらに `azimuthAngle` は `_spherical.theta`、つまり**注視点から見たカメラの角度**なので、注視点をずらすと基準が定数ぶん回り、`facingSection()` が隣のエリアを指すようになる。
- **採ったのは `CameraControls.setFocalOffset(x, 0, 0)`**。`node_modules` の実装（`camera-controls.module.js:2244-2257`）を読んで確認した通り、軌道を `_spherical` / `_target` から組み立て `lookAt` した**あと**に、カメラをカメラ自身のローカル軸方向へ平行移動する。`_spherical` も `_target` も触らないので、**公転の軸は島の中心のまま**・**`azimuthAngle` の意味も不変**。回転ではなく平行移動なので、ずれ量は回っても画面上で一定。
  - 符号は「+x でカメラが右へ動く＝被写体は左へ」。島を右に出すので**負**。`homeFocalOffsetX()` が `-aimOffset(...)` を返す形にした。
  - セクション側は `framePose` 自身の `sideways` で寄せているので、フォーカス時は**明示的に 0 に戻す**（二重に寄ってしまう）。自己紹介はこの経路なので特に重要。
  - リサイズ対応: ずらし量はフレーム**幅**に対する割合なので、ウィンドウ形状が変わると再計算が必要。R3F の `state.size` の同一性で「本当にリサイズしたときだけ」動く effect を1つ足した（`activeSection` は deps に入れてクロージャを新しく保つためだけ）。
- **`Canvas` の初期カメラ位置 `[18.4, HOME_HEIGHT, 18.4]` も直した**。18.4 は `26/√2`、つまり「半径26・方位45°」を手書きした値で、半径を変えても追従しない死んだ数字だった。`homePose(HOME_ANGLE).slice(0,3)` に置き換え。

#### 計測で踏んだ罠：紙吹雪をオブジェクトとして測っていた

- 最初の計測（左端・右端＝背景色と違う画素の min/max）は、**島の幅をフレーム幅の 83%** と報告した。これを信じて「余裕が11%しかない、大きく引かないと右が切れる」と判断し、半径を 26 → 29 まで引いた。
- 実際は**画面の隅まで漂う紙吹雪を測っていた**。列ごとの画素数を数え、フレーム高さの**1割**を超える列だけを採用するようにしたら、島の本当の幅は **57%** だった（自己紹介の構図合わせでも同じ罠を踏んでおり、そのときの閾値2%では紙吹雪の縦の重なりが通ってしまっていた）。
- **測り直して半径を決め直した**。share 0.22 のとき、半径26では最悪角度の右端が **98.2%**（＝実質フレーム端に接触、サンプルの隙間の角度で確実に見切れる）。半径 27.5 で **95.3%** になり、全角度で余裕が残る。29 まで引く必要はなかった。

### ズーム中はマーカーの点と点線を引っ込める

- **要望**: 点（マーカーのドット）をタップしてエリアにズームしたら、点と点線を消したい。
- **現状の実装がちぐはぐだった**: `AreaMarkers.tsx` は「フォーカスされたエリア**以外**のドットを 0 に縮める」ロジックで、選ばれたエリア自身のドットは残っていた（自己紹介だけが特例で消えていた）。点線は `hidden={pageOpen || activeSection === "about"}` だったので、ズームしただけ（`pageOpen` は false）では残ったままだった。
- **考え方を「マーカーは招待状」に統一した**。ドットと点線は「カードが指しているのはあそこ」と言うためのもので、カメラが着いてしまえば言うことは無い。`activeSection` があれば**全ドットを 0 に**（自己紹介の特例分岐はこれに吸収されて消滅）、点線も `pageOpen || !!activeSection` で外す。カード右上のアンカードットも、線が無いのに残ると迷子の点にしかならないので同時に消す。
- **踏んだ罠**: スポットライトのドットには「イージングしない」特例がある（`454c095` で入れたもの。点線の遠端が瞬時に飛ぶので、ドット側がイージング中だと線が何も指していないように見える）。そのまま全消しにすると、フォーカスした瞬間に**自分のドットだけパチッと消える**。特例は**入場方向にだけ**必要なので `isSpotlight && target > 0` に絞った。退場時は何も繋がっていないので他と同じくフェードする。

### 詳細ページ→ホームの遷移を、カメラが引き下がる動きとして見せる

- **要望**: 詳細ページからホームへ戻るときにカクつく。裏ではそのエリアにズームしているはずなので、ズームから俯瞰までカメラが引き下がる感じにしたい。

#### まずヘッドレスで測ろうとして、測れないことが分かった

- rAF の間隔を記録するスクリプトを書いて回したが、**3秒間で4フレーム**（333ms / 1233ms / 733ms / 750ms）しか回らなかった。ヘッドレス Chrome の SwiftShader はソフトウェアラスタライズなので、数千個のインスタンスと影のパスを1フレーム描くのに数百 ms かかる。**フレーム時間の計測にヘッドレスは使えない**（見た目の確認には使える）。
- 代わりに**コードから算術で詰めた**。`setLookAt(..., true)` は camera-controls の `smoothTime`（既定 0.25 秒）による臨界減衰。SmoothDamp は `t = smoothTime` で約 59%、`2·smoothTime` で約 91% 進む。一方シートの退場は framer-motion のばね（stiffness 280 / damping 34 / mass 0.9 → ω₀ = 17.6 rad/s, ζ = 1.07）で、画面から抜けるまで**およそ 0.3 秒**。
- **つまり、シートが退いた時点でカメラは既に6〜7割動き終わっている**。見えるのは残り3割が 0.2 秒で詰められるところだけで、「引く」ではなく「着地の残り」になる。要望の「カクつく」はこれだった。

#### camera-controls に任せるのをやめ、飛行を自前の時計で回す

- `smoothTime` を伸ばすだけでは直らない。SmoothDamp は**出だしが最速**の曲線なので、長くしても「シートの裏で大半が終わる」構造は変わらない。時間と曲線を自分で持つ必要がある。
- `worldLayout.ts` に純粋関数を2つ追加した。
  - `easeInOutCubic(t)` — 両端で止まり、真ん中が速い**対称な**曲線。シートが退く 0.3 秒（1.2 秒の飛行の 25%）の時点でまだ **9.4%** しか進んでいないので、見えるようになってから引きの大半が残っている。
  - `glidePose(from, to, t)` — 2つの構図の間を、位置の線形補間ではなく**注視点まわりの軌道**（半径・伏角・方位）で補間する。
- **位置を lerp してはいけない理由**: 弧の2点を結ぶ直線は弦で、弦の中点は弧の**内側**に入る。建物から俯瞰へ引くのに、途中でいったん街へ**近づいて**しまう。実測でホームボタンの飛行（方位も回る）は 20% 地点で 9 → 8.2 ワールド単位と内側に入っていた。
- **`CameraControls.lerp()` は使えなかった**。球面補間まではしてくれるが、両端の方位を `atan2` で復元して**生のまま引き算する**（`camera-controls.module.js:1786`）。±π をまたぐ2つの構図は近いのに 300°以上回る。自己紹介は回り続けるので、そこから HOME を押すと現実に起きる。既存の `wrapAngle()` を通すだけの違いだが、これが理由で自前にした。
- **飛行の長さは「何かが画面を覆っていたか」で決める**（どのボタンを押したかではない）。シートが退くのを待つ必要がある経路だけ 1.2 秒、待つものが無ければ 0.8 秒。`pageOpen` の**前回値**が要るが、この effect は `pageOpen` では再実行しない（させたくない）ので、**行き先を決める effect の後ろに**専用の effect を1つ置いて ref を更新する。宣言順で「前回値を読んでから更新する」が保証される。カードをタップして開く場合は `activeSection` が変わらず行き先の effect が走らないため、ここを1行で済ませることはできない。

#### 遅延フレームで飛行が飛ばないようにする（と、やりすぎて直した）

- 詳細ページの裏では `frameloop="demand"` で**毎秒1フレーム**しか回らない。そこから戻る最初のフレームの `delta` は最大1秒近くあり、そのまま食わせると1フレームで飛行がほぼ終わる。
- 最初 `MAX_FLIGHT_STEP = 1/30` でクランプしたが、これは**30fps を下回る端末で飛行が丸ごとスローモーションになる**。ヘッドレス（約3fps）で計ったら 1.2 秒の飛行が**12 秒**かかっていた。
- 正しい会計に直した。`delta` は「**前**フレームからの経過」で、飛行は effect の中＝フレームとフレームの間で始まる。**その経過は飛行の時間ではない**。最初の1フレームは加算しない（`primed`）ことにして、クランプは 1/10 まで緩めた純粋な保険にした。

  - 最初は「280ms ごとに1歩なら連続スクロールでも送れる」版を書いたが、**同じテストファイルの中で矛盾した**（「一振り＝1枚」と「連続なら複数」は両立しない）。1歩がカメラの回転を伴う以上、1ジェスチャ1枚が正しい。
- **フォーカス中は重ねも送りも引っ込める**。カメラは建物に駐まっていて軌道もロックされているので、送っても**視界と違うエリアのカードになるだけ**だった（従来のスワイプも同じく不発だった）。板を消して「これ1枚」と言わせる。
- **計測の罠**: Puppeteer の `page.mouse.wheel` を `await` で1つずつ送ると、CDP の往復で間隔が 220ms を超え、**毎回が新しいジェスチャ**として扱われて1度も送られなかった（1イベント 60 < 閾値 80）。`Promise.all` で詰めて送ったら期待通り「一振り＝1枚」になった。実機のホイールは1クリック 100〜120、トラックパッドは 10〜16ms 間隔なので現実には起きない。

### 点線がドットからずれる問題の再発 — カードのアニメーションで anchorRef が null になっていた

- **症状**: スクロール中と自動回転中に、点線がドットからずれる。一度直したはずの問題（`754f0f4`）の再発。
- **原因は今回の変更**。カードを `AnimatePresence` で包んだため、`facing` が変わるたびに `key={section}` のカードが**作り直される**。`popLayout` では退場するカードがしばらく DOM に残るので、**入場側が `anchorRef` をセットしたあとに、退場側の ref コールバックが `null` で呼ばれる**。結果 `anchorRef.current` が空になり、`CardLeaderLine` の `draw()` が毎フレーム先頭で `return` して、**ポリラインが最後に描かれた位置のまま凍る**。カードが1回でも切り替わると以降ずっと固まるので、「スクロール中と自動回転中」＝エリアの境界をまたぐときに出る、という症状になる。
- **切り分けた手順**（推測で直さないために計測した）。`AreaMarkers` に一時的な計測口を開け、同じフレームについて「シーンが publish した座標」「点線の終端」「ドットの画素重心」の3つを比べた。

  | | シーンの publish | 点線の終端 | ドットの画素 |
  | --- | --- | --- | --- |
  | 停止中 | (779, 504) | (1008, 516) | (779, 504) |

  **publish と画素は 0px** ＝ 射影は完全に正しい。ずれているのは点線だけで、しかも回転中と停止中で**終端が同じ値**だった＝**描き直されていない**。ここで「射影のズレ」ではなく「更新が止まっている」と分かった。
- **前回の `updateMatrixWorld()` の修正は無関係で、いまも正しく効いている**（停止中に publish と画素が完全一致するのがその証拠）。フレーム順序も確認した: drei の `CameraControls` は `useFrame(..., -1)` で**優先度 -1**、つまり毎フレーム最初に `controls.update()` が走ってからマーカーが射影するので、1フレーム遅れは発生しない。
- **直し方**: アンカーの点を**カードの中からスタックのコンテナへ移した**。印しているのはカードの角だが、動かないのはスタックのほう。コンテナは作り直されないので ref が二重に持たれることがない。副次的に、カードが入れ替わるアニメーション中も線の起点が動かなくなる。
- **同じ失敗を静かに起こさないようにした**: `CardLeaderLine` の `draw()` は、アンカーが無いとき `return` するのをやめて**線を消す**ようにした。古い線が残るほうが悪い壊れ方で、シーンだけが下で動いていくため「線がドットから外れた」ように見える。消えていれば何かが無いことがすぐ分かる。
- **検証**: 4エリアをまたぐ14サンプルで、点線の終端とマーカーの距離が期待値（`radius + MARKER_GAP + CAP`）と**すべて 0.1px 以内**で一致することを確認した。
- **画素でドットを探す計測には限界がある**（最初これで測って2件の偽陽性を出した）: オレンジの紙吹雪や、停止中にオレンジになる一時停止ボタンを拾う。マーカーが画面上端に来ると探索範囲から外れる。**シーンが publish した座標を突き合わせるほうが正しいオラクル**。

### 自己紹介を「画面いっぱいに流れる列」にし、帰り道をスクロールに握らせる

- **要望**: (1) 自己紹介文は画面下から画面上まで表示する。(2) ホームへの遷移は文章の半分あたりからカメラが少しずつオブジェクトに寄り始める。(3) **完全にホームへ戻るのは、文章が完全に画面上までスライドされた瞬間**。
- **列を全画面高にした**（`About.tsx` / `page.tsx`）。ラッパーを `top-1/2 -translate-y-1/2` から `inset-y-0` に、列を `max-h-[72vh]` から `h-full` に。実測でスクローラは `top:0 / bottom:950`＝ビューポートそのもの。
- **末尾に1画面ぶんの空白を足した**のが今回の要。これが無いと最後の行は画面の下端で止まり、「文章が画面上まで抜ける」状態にならない。あわせて**進捗の意味が変わる**: `scrollHeight - clientHeight` がちょうど本文の高さになるので（実測 2454 − 950 = **1504 = 本文の高さ**）、進捗は「本文のどれだけが画面上端を通過したか」そのものになる。**半分読んだ＝半分消えた＝半分帰った**が同じ数になり、カメラの補間にそのまま使える。
  - 空白は `h-screen` ではなく **`h-full`**。スクローラの高さと**1px も違ってはいけない**（違えば進捗1が「本文が消えた瞬間」でなくなる）。100vh はモバイルのツールバーぶんずれる。
- **帰りの飛行をやめ、スクロールに握らせた**（`aboutScroll.ts` の `aboutReturnProgress()` と `Scene.tsx` の About 分岐）。0.5 までは 0、そこから 1 まで線形に上がる値を `easeInOutCubic` に通し、毎フレーム `glidePose(自己紹介の構図, homePose(現在の方位), t)` を組む。読者が時計を握っているので**上へ戻せばカメラも引き返す**。
  - **両端は毎フレーム現在の方位から組み直す**。開始時に固定すると、半分を過ぎた瞬間に自動回転が止まって見える。
  - 焦点オフセット（ホームの右寄せ）も同じ曲線で 0 → `homeFocalOffsetX` へ運ぶ。**t=0 でも毎フレーム書く**——書かない分岐にすると、上へ戻したときに寄せが最後の値のまま残る。
- **着地したらもう飛ばない**。`onFinish` は `closeToHome` ではなく `closePage` だけを呼び、`Scene.tsx` の唯一の effect に「`cameFrom === "about"` かつ帰りの進捗が1なら飛ばない」分岐を足した。ここで飛ばすと**自己紹介の方位へ回り直す**という、読者が既に済ませた到着の上塗りになる。正面のエリア（`facing`）だけは、止まった方位から計算して publish する（自由回転は変化時にしか publish しないため）。
- **計測（一時的な計測口を `useFrame` に開けて、停止ボタンで街を止めて測った）**:

  | --- | --- | --- | --- | --- |
  | 0.00 / 0.25 / 0.50 | 40.80 | 21.15 | −1.70 | 0.00 |
  | 0.60 | 40.41 | 20.76 | −1.53 | −0.13 |
  | 0.75 | 34.71 | 15.61 | 0.90 | −2.08 |
  | 0.90 | 29.01 | 11.66 | 3.33 | −4.02 |
  | 着地 | **28.62** | **11.44** | **3.50** | **−4.15** |

  ホームの理論値は距離 `HOME_DISTANCE = 28.62`・高さ `HOME_HEIGHT = 11.44`・注視点 `HOME_TARGET_Y = 3.5`・オフセット −4.1514。**着地と `homePose(方位)` の差は全軸 0.0000**、オフセットも一致。前半3点が完全に同値なのは「半分までは動かない」の実測。着地から3秒後も **0.0000 しか動いていない**＝あとから飛行が走っていない。
  - 0.00 の距離が `ABOUT_DISTANCE = 39.32` ではなく 40.80 なのは、`framePose` の `sideways` が注視点を横へずらすため。`hypot(39.32, 10.89) = 40.80` で説明がつく（バグではない）。
- **入場中のフリックで詰む穴を塞いだ**（`settleRetryDelay()`）。`ABOUT_SETTLE_MS`（500ms）以内に来たスクロールは弾かれるが、**下端まで飛ばした後はもうスクロールイベントが来ない**ので二度と聞き直せない。今までは「本文の末尾で止まる」だけだったが、本文が画面から消える今回の作りでは**空の画面に取り残される**。窓が閉じるまでの残り時間だけ待って、列の**現在位置を読み直して**判定し直す。

### 自己紹介のスクロールを半分の速さにする

- **要望**: 自己紹介文のスクロールが速すぎる。
- **ホイールを自前で受けることにした**（`aboutScroll.ts` の `wheelScrollStep()`、倍率は `ABOUT_SCROLL_RATE = 0.5`）。今まで `preventDefault` を**しない**のがこの列の方針だった（既定動作こそがスクロールだから）が、速度を決めるにはこちらが動かすしかない。`stopPropagation` は従来どおり必要（シーンが `window` でホイールを聞いていて、放っておくと同じ操作で街も回る）。
- **理由**: この列はただの長文ではなく**カメラの帰り道そのもの**。ブラウザ既定の速さだとトラックパッドの一振りで本文の大半を通過し、後半の「少しずつ寄る」が一瞬で終わる。半分にすると、一振りが1ページではなく1段落ぶんになる。
- **`deltaMode` を先に正規化してから倍率を掛ける**。Firefox の delta は**行**単位（1ノッチ = 3行）で、3 を3pxと見なして 0.5 倍すると**ほぼ動かなくなる**。行は 40px、ページは読者のビューポート高で換算する（ページだけ固定値にすると背の低い画面で行き過ぎる）。
- **引き換え**: マウスのノッチ1段ぶんをブラウザがアニメーションしてくれる分は失う（1段が1回の跳びになる）。細かい delta を連射するトラックパッドは滑らかなまま距離だけ縮むので、主な操作系では影響が出ない。**タッチは既定のまま**にした——指に 1:1 で追従しない慣性は「遅い」ではなく「重い」と感じられるため。
- **検証**: `npm test` 174件（新規5件）／lint／`tsc`／`build` クリーン。ヘッドレスで実際にホイールイベントを投げて実測: 100 のノッチ10発で **500px**（既定なら約1000px）、上向き4発で −200px、行モード（delta 3）3発で **180px** = 3 × 3行 × 40px × 0.5 と一致。下端まで送ればこれまでどおりホームに戻ることも確認（スクロールイベントは 492ms で届き、列はその後アンマウント）。コンソールエラーなし。
- **変異テスト4件**（倍率を1に／`deltaMode` を無視して全部 px 扱い／ページ換算を固定値に／符号を落として上へ戻せなくする）。すべて落ちることを確認した。テストは**リテラルで書いてある**——`ABOUT_SCROLL_RATE` を使って書くと倍率1（＝ブラウザ既定＝今回消したかったもの）でも緑になる。

- **要望**: ズームした後にホームへ戻るときと、詳細ページからホームへ戻るときのカメラが「一瞬左上あたりへ切り替わり、そこから戻る」ように見える。ロゴをタップして自由視点からホームへ戻る挙動（既定角への着地）や、自己紹介を読み切って戻る挙動は良いとのこと。

- **直した**: `Scene.tsx` の行き先 effect で、「明示的なリセット」の分岐条件に `!(cameFrom && sectionTargets[cameFrom])` を足した。エリアを離れる先がある（ズーム中、または詳細ページを開いていた）場合はこの分岐を素通りして、既存の「4. エリアを離れる」分岐（スクロール離脱と共用）に合流し、そのエリア自身の方位角へ引く。エリアが無い（既に自由視点）場合だけ、これまで通り固定の `HOME_ANGLE` へ着地する——ロゴタップで自由視点から既定角へ戻る、良いと言われた挙動はそのまま。
- **検証**: `npm test` 174件／lint／`tsc`／`build` すべてクリーン。上記の計測トレースで軌道が直線的な引きに変わったことを確認。

### 長く残っていた「ズームイン・ズームアウトでカメラが少し左に飛ぶ」の原因を特定して直した

- **要望**: 点を押してエリアへズームインするとき／エリアから HOME でズームアウトするとき／詳細ページからホームに戻るとき、3つすべてで**カメラが少し左に飛ぶ**。長期間解決できていないので、根本的な問題も視野に入れて調べ直してほしい。
- **決め手になったユーザーの観察**: 「**ズームインしきる前にズームアウトすると滑らかになる**」（飛行中に HOME を押す／ヘッダーを押した直後にスクロールで戻る）。これが後述の原因を一発で説明する。
- **原因は焦点オフセット（ホームの右寄せ）が飛行の1フレーム目に瞬間移動していたこと**。`Scene.tsx` の「リサイズしたら寄せを再計算する」effect が、判定を `lastSizeRef.current === size`（**参照比較**）で行っていた。`useThree` の `size` は**リサイズでない再レンダーでも新しいオブジェクトとして返ってくる**ため、この判定は常に「リサイズした」になり、`snapFocalOffset()`＝寄せを行き先の値へ**スナップ**する処理が毎回走っていた。しかもこの effect は行き先を決める effect より**前**に宣言されているので、順番はこうなる:
  1. エリアをフォーカス（または離脱）→ 再レンダー
  2. リサイズ用 effect が誤発火し、焦点オフセットを**行き先の値へ瞬間移動**
  3. 直後に行き先の effect が `startGlide()`。開始値を `getFocalOffset()` から読むが、**もう行き先の値になっている**
  4. `fromOffsetX === toOffsetX` なので寄せは飛行中まったく補間されず、**2で起きた瞬間移動がそのまま横跳びとして見える**
- **なぜ「飛行中に次を始めると滑らか」なのか**: リサイズ用 effect は飛行中だけ別分岐（`if (glide) glide.toOffsetX = focalOffsetX()`）に入り、**スナップしない**。だから飛行が終わる前に次の遷移を始めると瞬間移動が起こらない。ユーザーの観察と完全に一致し、これが仮説の裏取りになった。
- **調査の進め方**: 最初に疑った2つは計測で**否定した**。(1)「`getPosition()` が焦点オフセットを含んだ位置を返していて二重適用になっている」→ `camera-controls` のソースを読むと `getPosition` は `_spherical` + `_target` から組み直す＝軌道上の純粋な位置で、オフセットは含まない。`setLookAt` もオフセットに触らない。(2)「state 更新と effect の間の1フレームでアイドル回転が暴れている」→ 毎フレームどの分岐がカメラを書いたかタグ付けして記録したが、クリックと飛行開始の間にアイドル分岐のフレームは**存在しなかった**。方位角・距離の差分もきれいな `easeInOutCubic` の釣鐘型で、飛行自体は数学的に滑らかだった。
- **効いた計測方法**: 方位角や距離ではなく「**画面に何が出ているか**」を直接測ったこと。`CameraControls` の `update()` より**後**に走る一時的なプローブ（ツリー上で `CameraController` の後に置くと `useFrame` の登録順で後になる）を足し、固定のワールド点（島の中心）を毎フレーム射影して**画面X座標**を記録した。ここで初めて1フレームの不連続が見え、同じ行に出ている `offX`（焦点オフセット）が犯人だと分かった。さらに `startGlide` と `snapFocalOffset` にログを入れると、**同一ミリ秒**で `SNAP OFFSET` → `GLIDE START (fromOffsetX === toOffsetX)` の順に並び、確定した。

  | 遷移 | 修正前（島の画面X） | 修正後 |
  | --- | --- | --- |
  | ズームイン | 781 → **640（1フレームで −141px）** → その後 838 まで戻る | 781 → 781 → 780 → 774 → 760 …（最大 −38px/フレーム、3fps計測） |
  | ズームアウト（HOME） | 838 → **1002（1フレームで +164px）** | 838 → 838 → 835 → 828 …（最大 16px） |
  | 詳細ページ → ホーム | 同じ（0 → −4.17 が一瞬） | オフセットが 0 → −0.03 → −0.11 → … → −4.17 と滑らかに乗る |

  修正前は「**左に141px跳んでから右へ198px戻る**」という軌跡で、これがまさに「少し左に飛ぶ」の正体だった。
- **直し方**: 判定を寸法比較にした。`worldLayout.ts` に純粋関数 `frameSizeChanged(prev, next)` を切り出し、`lastSizeRef` は寸法だけを保持する。高さも見るのは、幅が同じでもアスペクトが変われば `homeFocalOffsetX()` の値が変わるため。
- **検証**: `npm test` 177件（新規3件）／lint／`tsc`／`build` すべてクリーン。上の3遷移すべてをヘッドレスで再計測して跳びが消えたことを確認（詳細ページ経路は `wasCovered` の1.6秒と `frameloop="demand"` も通る）。**変異テスト**: `frameSizeChanged` を参照比較 `(prev as object) !== (next as object)` に差し替えると、177件のうち**今回書いた1件だけ**が落ちる（「別オブジェクトで同じ寸法はリサイズではない」）——このバグを射抜くテストになっていることを確認した。退避は `cp` で行い、`git checkout` は使っていない。
- **変異テストで確認**: `ABOUT_SCROLL_RATE` を一時的に `0.5` に戻すと、直した4件がすべて意図通り落ちることを確認してから `0.2` に戻した。`npm test` 174件全件通過・lint・`tsc` クリーン。

### 参考画像（`reference/image3.png`）の計測で、決めたばかりの数値が2つ否定された

- ユーザーから惑星の参考画像が追加された。球体に都市がびっしり立ち、建物が全方向へ放射しているティルトシフト風の惑星。
- **切り出しに2回失敗してから、方法を変えて成功した。** 背景が一様ではなく**中央が明るいグラデーション**（四隅 `105,160,189` 〜 中央付近 `134,188,220`）だったのが原因。
  - **失敗1: 四隅から背景色を取って固定しきい値** → 背景の振れ幅（差の合計で88）がしきい値40を超えるため、画面の89%が「前景」になった
  - **失敗2: 画像の縁からの領域拡張（1歩あたりの差が小さければ広げる）** → 縁のアンチエイリアスが1歩あたりの差を小さくするため、背景が惑星の内部まで漏れた。連結成分が1528個に割れ、最大でも画面の0.4%
  - **成功: 中心から720方向にレイを引き、外から内へ歩いて「ゆっくり動く背景推定値から段差で外れた最初の半径」を取る** → グラデーションは1pxあたり1未満しか動かないので、しきい値35の段差は物体の縁しか作れない。透かし文字の一本線を拾わないよう、内側が6px続けて背景から離れていることも条件にした
- **計測結果**（地表の半径 = 谷の p5 = 300px）:

  | 項目 | 実測 |
  | --- | --- |
  | 建物の高さ 中央値 | 地表半径の **+17%** |
  | 同 p90 | **+24%** |
  | 同 最大 | **+30%** |
  | 地表がむき出しの方向 | **26%** |

- **否定1: 建物が高すぎた。** 「惑星の世界半径 22 なら products タワーが 46% に落ちて『惑星に建つ塔』として読める」と書いたが、参考の**最大でも 30%**。46% は参考のどのビルよりも高い。**惑星の半径を 34 に改めた**（タワーがちょうど 30%）。建物側は一切いじらない——他のセクションも 9〜19% に収まり、参考の中央値 17% を挟む形で散る。
  - あわせて voxelSize を 1.0 → **1.4** に上げた。`R=24 / vs 1.4 / 厚2` で **13,304 voxel**、世界半径 33.6。当初案（11,072）と大差ないブロック数のまま比だけが正しくなる。ブロック1段が世界半径の 4.2% なので、球の階段が明確にボクセルとして読めるという副産物もついた。
- **否定2: セクション建物5つだけでは、この見た目にならない。** 参考の主役は**リムから突き出るシルエット**で、**74%の方向に何かが立っている**。5つでは惑星がほぼツルツルに見える。**名前を持たない雑居ビルの群れを構成要素として追加**することにし、手順3として独立の段階に切った。密度は「地表がむき出しの方向 26%」を目標に、同じ720方向のレイで測って決める。
  - **`VoxelModel` に回転が要ることが分かった。** 現在は各ボクセルを `v.x * voxelSize` に置くだけで、**共通の格子の上にしか並べられない**。雑居ビルは1棟ごとに違う法線を向くので、この形では1つのメッシュにまとめられない。インスタンス行列は元から任意の回転を書けるので、ボクセルが位置と回転を自分で持つ変種を足せばドローコールは1のまま済む。
- **参考画像の背景が宇宙ではないことに気づいた。** 明るいブルーグレーで、**シルエットの読みやすさはこの明るい背景にかなり助けられている**。暗い宇宙背景で同じことをすると輪郭が背景に溶ける。逆光のリムライトを入れるか建物の明度で稼ぐ必要があり、リスクとして記録した。うちのパレットがパステルで明るいのは有利に働く。
- **他に読み取ったこと**: 建物は全球均等ではなく**クラスタ（都市）**で散り、間に何も無い海がある。地表には起伏と海陸があり単色の球ではない（球殻の生成でノイズを色だけでなく**高さ**にも効かせる）。建物の向きは完全に法線方向で、「緯度の高い建物が斜めに見えるのは仕様」という判断が裏づけられた。

### 手順1: `scene/planet/` の純粋ロジックとテスト（画面は変わらない）

- `planetLayout.ts`（経緯度→単位方向・接空間の基底・フィボナッチ散布・大円回転・slerp）、`sections.ts`（各セクションの経緯度とヨー角）、`tour.ts`（経路）、`shell.ts`（球殻と地形）を追加。**テスト93件追加**（177→270件）。three.js も React も含まないので node のまま走る。
- **回転はクォータニオンではなく接空間の基底ベクトル3本（数値配列）で返す**ことにした。`THREE.Quaternion` を返すと node のテストに three が入ってしまう。three への変換は React 側の `Matrix4.makeBasis` に任せる。基底が右手系（`right × up === forward`）であることをテストで固定した——**符号を間違えると全建物が鏡像になり、鏡像のボクセル箱は見た目で気づけない**（看板の文字が裏返って初めて分かる）。

#### 経路をベクトル空間で組むと、カメラが緯度71度まで潜っていた

- 最初の実装は**5点の最短巡回路**を総当たりで求め、**方向ベクトルを Catmull-Rom で補間して正規化**した。球面上に滑らかな閉曲線を引く教科書的なやり方。アンカーの緯度は -48〜42 なのに、**経路は -71.4〜66.2 まで振れた**。安全域（`camera.up` が +Y なので極付近で `lookAt` が退化する）の ±60 を突き抜けている。**レンダラを立てる前に、純粋ロジックのテストだけで見つかった。**
- **スプラインのオーバーシュートではなかった。** テンションを 0.5→0 まで下げて（＝区間ごとの大円そのものにして）測っても -71.0。原因は**大円が両端より極側へ膨らむ**という球面幾何そのもの。東京〜NY 便が北極を通るのと同じ。南緯40度の2点で実測:

  | 経度差 | 36° | 72° | 100° | 144° | 170° |
  | --- | --- | --- | --- | --- | --- |
  | 膨らみ | 1.4° | 6.0° | 12.5° | 29.8° | 44.1° |

- **犯人は2つあり、大きい方は巡回順だった。** 最短巡回路は「南の2つを144°離れたまま直接結ぶ」順番を選んでいて、その1本の脚だけで29.8°潜っていた。**経度順**に並べ直すと脚が 360°/n ≒ 72° に収まり、同じアンカー・同じベクトル補間でも -48.1 まで戻る。
- **それでも緯度経度の空間で補間する方に変えた。** 膨らみが小さくなるのと消えるのは別の話で、後者でないと**「経度の並びが均等かどうか」に緯度の上限が依存する**。手順2でスクリーンショットを見ながら位置を詰めるのに、建物を1つ東へ動かしたらカメラが10°南へ落ちる、という隠れた結合は最悪のタイミングで露見する。緯度経度で組めば残るのはスプラインの 1.2° だけ。
- **最短巡回路の実装は書いて捨てた。** 経度が逆走する順番を選びうるので、「一周＝一回転」というスクロールの前提が壊れる。経度順なら緯度がすべて0のとき今のリングにそのまま縮退するので、`SECTIONS_BY_AZIMUTH` の考え方も引き継げる。
- **暫定座標も直した。** 最初は +42, -34, +26, -48 と交互に振っていて、一周で60〜76°の緯度スイングが3回起きるジェットコースターだった。傾斜軌道のように一方向へドリフトして戻る並び（6, 38, 30, -18, -44）に変更。経路長は 7.87 → **6.326 rad**（大円一周 6.283 の 0.7%増）に落ち、「衛星の軌道」として読める形になった。
- **経路は弧長でパラメータ化した。** スプライン自身の `t` はコーナーで速く直線で遅いので、同じ量スクロールしても場所によって進む距離が変わる。密にサンプリングして累積弧長で引き直した結果、1/500 刻みの区間長のばらつきは **0.02%**。

#### 地形のノイズは方向の関数でなければならない

- 島の `noise2(x, z)` に相当するものを緯度経度で書くと、球には**2つの継ぎ目**が出る: ±180°の子午線に沿った崖と、極の**風車模様**（あらゆる経度が1点で出会うのに、ノイズが同じ点について別々の高さを返す）。**方向ベクトルの成分の関数**にすればどちらも原理的に起きない。両方をテストで固定した。
- **石の色の分岐が死んでいた。** 境目を `depth < 2` と固定の深さで書いていたが、殻の厚みが2なので深さ2に届くブロックが存在せず、**13,525個のうち0個**が石だった。境目を厚みに対する割合にして解消（土 24%／石 24%）。ブロック数や貫通率では絶対に気づけない種類のバグで、色の内訳を数えて初めて見えた。
- **実測**: 起伏込み **13,525 ブロック**（起伏なしの球なら 13,304 で、計画の予測値と一致）。貫通穴は**厚2で 0.00%、厚1で 3.82%**——計画段階の見積り（3.4〜4.1%）とも合っている。海は面積の28%。

#### 変異テスト25件、生き残りは1件

- `planetLayout` 7件・`tour` 9件・`shell` 9件を仕込み、**24件は意図通り落ちた**。退避は `cp`、復元も `cp`（`git checkout` は使っていない）。毎回 `diff -q` で元に戻ったことを確認。
- **1件だけ生き残った**: 「経度の巻き戻しをやめる」。`buildTour` に渡すアンカーがテストでは常に経度昇順だったので、巻き戻しが無くても差が出なかった。**テストの穴**なので、経度が昇順でない並び（200°, 10°, 130°）を渡して「一周だけ前進する」ことを見るテストを追加し、射抜けることを確認した。
- 数字を書いたコメントは実測で裏取りしてから残した。**2箇所が間違っていた**: 正規化 lerp の区間弧を 0.1330/0.1749 と書いていたが実際は 0.1107/0.1974、フィボナッチ球100点の最近接を「約0.35」と書いていたが最小 0.310・平均 0.337（比較対象の `hash01` 散布は 0.010 で、30倍近い）。

- **`npm test` は 431ms → 約1.1秒**（270件）。CLAUDE.md と tech.md の「1秒未満」の記述を実測に合わせて更新した。

### 手順2: 土台を惑星に差し替え、建物を再着地させた（画面が初めて変わった）

- `scene/Planet.tsx`（`planetVoxels()` を1つの `VoxelModel` に渡すだけ）で `VoxelIsland` を置き換え、5つの建物を `sectionPosition()` / `sectionBasis()` の位置・向きで再着地させた。カメラの**仕組み**（`Scene.tsx` の azimuth-ring モデル）は手順4まで一切触っていない——変えたのは建物の位置・向きと、`worldLayout.ts` の `HOME_RADIUS` 系の**数値**だけ。
- **`BUILDING_POSITIONS` の値を差し替えただけで、下流が無傷だったのは手順1の設計が効いた結果**。`sectionAzimuth` が読むのは `atan2(x,z)` だけで、`latLonToDirection` の規約では緯度によらず厳密に経度そのものになる（`cos(lat)` が共通の正の係数として消える）。`sectionTargets` / `facingSection` / `SECTIONS_BY_AZIMUTH` / `adjacentSection` / `homePose` / `framePose` を1行も変えずに新しい球面座標で動いた。`worldLayout.test.ts` も無変更で283件（変更前と同じ件数）通過。
- **ホームの距離を最初、旧居との比を保つやり方（66/19/0）で計算したが、スクリーンショットを見たら惑星のごく一部に張り付くほど近すぎた。** 原因は `frameDistance()` の意味（`asin(半径/距離)` が視野角の半分を超えると画面をはみ出す）を無視して、非対称な平べったい旧い島の「タンジェント球」直感を、そのまま対称な新しい球に当てはめたこと。`frameDistance(33.6,45,1.6)≈87.8`（惑星が垂直視野いっぱいに収まる最短距離）に対し、最初の66はその75%——はみ出して当然だった。「フレーム幅の35%を占める」という目標角度から距離を逆算し直し、`HOME_RADIUS=158.6` / `HOME_HEIGHT=45.8` / `HOME_TARGET_Y=0` に。`ABOUT_RADIUS` は `HOME_RADIUS` との比（32/27.5≈1.164）を保って185に。`maxDistance`・フォグ・影のカメラ範囲も距離が伸びたぶん一時的に広げた（宇宙化する手順5で作り直す前提の応急処置と明記）。
- **一周ぶん6角度をヘッドレスで撮って確認**: 惑星がフレームの右77%程度までに収まり、上端24%、どの角度でも縁に触れない。`facingSection` の切り替わりに合わせてカード・点線・マーカーが正しく追随することも確認できた（自己紹介・制作実績・お問い合わせのカードが対応する建物の正面で正しく切り替わった）。
- **自動計測を書いたら、フッターの著作権表記と左下のアイコンボタンを「惑星のシルエット」として誤検出した。** 回転しても値が94.9〜95.0%からほぼ動かない——固定位置のDOM要素だから当然で、3D側ではなく計測スクリプトの色しきい値の甘さが原因だった。devlog 7/29 の点線計測（「画素でドットを探すと紙吹雪や一時停止ボタンを拾う」）と同じ失敗の再演。すでに6角度を目視確認していたので、そちらを正としてこの計測は捨てた。
- **`products` にズームすると建物が地面から浮いて見えた。** 座標を直接計算して追跡:
  - 建物の土台（アンカー）は惑星中心から33.11世界単位、最寄りのクラスト・ボクセルまで**0.98世界単位**——法線・位置とも数値上は正しい（回転が鏡像になっていないか、台座が逆方向に伸びていないかも検算した）。
  - 崩れているのは**セクション・ズームのカメラ**（`framePose` 経路）の方だった。台座を足すと `products` のバウンディング球の半径が6.93→9.68世界単位（+40%）に膨らみ、`frameDistance()` の距離も24.43→34.15に伸びる（中心点は台座に引かれてむしろ anchor 側へ寄る: 38.67→36.12——「浮いて見える」の説明としては半径・距離の膨張のほうが大きい）。`framePose` は世界の+Yを基準にした方位角・仰角で位置を組む式で、この膨らんだ的と距離を渡すとどう壊れるかまでは追い切れていない（追う価値もない——`framePose` はどのみち手順4で全面的に置き換わる）。
  - ホーム（全景）の構図は無傷。壊れているのはズームだけで、新しい不具合というより、計画書に最初から書いていた `framePose` の限界が台座によって早く露見しただけ。
